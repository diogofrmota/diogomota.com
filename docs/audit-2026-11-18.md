## Confirmed: shared infrastructure and authentication

### F01 — High: Switching apps can discard another app's queued changes

**Affected apps:** all five apps through the shared persistence provider.

**Locations:**

- `app/components/common/QueryProvider.tsx:19` — storage key.
- `app/components/common/QueryProvider.tsx:55` — independent QueryClient creation.
- `app/components/common/QueryProvider.tsx:84` — automatic mutation replay.
- `app/components/fitness/FitnessApp.tsx:105` — Fitness-specific setup.
- `app/components/books/BooksApp.tsx:91` — Books provider without mutation setup.

**Evidence:** Every app creates its own QueryClient but persists to the same `diogomota-cache:<userId>` key. Each registers only its own mutation handlers; Books registers none. Restoring another app's queued mutations and calling `resumePausedMutations()` attempts to execute mutations without their handlers. Separate tabs can also overwrite the shared snapshot with independent client states.

An isolated reproduction using the installed library produced:

```text
Before: 1 persisted mutation
After resume: status=error, error="No mutationFn found"
Next persisted snapshot: 0 mutations
```

**Impact/trigger:** Queued work can disappear when a user switches apps before synchronization. The error may belong to another app's mutation key and not be shown by the current app.

**Reproduction:** Queue a Fitness change offline, allow persistence, close that page, reconnect and open Books before Fitness. Inspect the persisted mutation and subsequent server state. Also test independent app tabs writing snapshots concurrently.

**Recommended fix:** Isolate storage by user and app, or use a genuinely shared client with every handler registered before hydration. Migrate existing snapshots without discarding pending mutations. Explicitly handle cross-tab ownership. Coordinate with F02 and F08.

**Acceptance criteria:** Queued changes survive app switching, reloads and simultaneous tabs; each reaches the correct API exactly once; no unknown-handler mutation disappears silently; existing persisted snapshots migrate without loss.

**Reference:** [TanStack mutation persistence documentation](https://tanstack.com/query/latest/docs/framework/react/guides/mutations).

### F02 — High: Every release can delete unsynchronized changes

**Affected apps:** every app using persisted mutation queues.

**Locations:** `app/components/common/QueryProvider.tsx:76`, `app/Dockerfile:55`, `.github/workflows/deploy.yml:72`.

**Evidence:** The persistence `buster` is `APP_VERSION`, which changes with every deployment. The snapshot contains disposable query results and unsynchronized mutations. A version mismatch removes the entire snapshot. An in-memory restore from `v1.2.1` into `v1.2.2` confirmed that the snapshot was removed and zero mutations were restored.

**Impact/trigger:** A deployment between offline editing and synchronization silently loses queued user work, even if the release did not change the data format.

**Reproduction:** Persist an offline edit on one release, deploy another release in an isolated environment, then reopen online before the edit synchronizes.

**Recommended fix:** Separate durable pending operations from disposable caches. Use explicit data-format versions and migrations rather than release numbers. Retain unsupported operations in a recoverable, visibly reported state. The first release of the fix must migrate old snapshots rather than invalidate them.

**Acceptance criteria:** Pending edits survive a normal patch deployment. Incompatible formats produce a recoverable migration/error state, never silent deletion. Query-cache invalidation does not delete pending operations.

**Reference:** [TanStack persistence documentation](https://tanstack.com/query/latest/docs/framework/react/plugins/persistQueryClient).

### F03 — High: Password-change logout leaves private offline data accessible

**Affected apps:** account settings and all cached authenticated apps.

**Locations:** `app/app/account/actions.ts:123`, `app/components/account/AccountSettings.tsx:208`, `app/components/common/QueryProvider.tsx:32`, `app/public/sw.js:38`.

**Evidence:** Changing a password revokes sessions, signs out the current browser and redirects to Login. Unlike explicit logout, this flow never clears localStorage or service-worker caches. Cached HTML is keyed only by URL, not account, and contains the previous user's app props. An offline revisit can restore that user's persisted data despite the local password-change logout.

**Impact/trigger:** A subsequent user of the same browser can encounter the previous account's cached view. This concerns local cleanup on an explicit successful session transition; it is not a claim that a disconnected device can immediately observe remote session revocation.

**Reproduction:** In an isolated production build, load an app as A, change A's password, verify logout, disconnect and reopen the cached app URL. Also test logging into B before disconnecting. The authenticated browser reproduction was not performed during the audit.

**Recommended fix:** Centralize successful session-transition cleanup. Stop persistence, clear account data and authenticated documents, await completion and coordinate other tabs. Prevent pending persistence writes from recreating cleared state. Do not erase pending work merely because a password-change attempt failed validation.

**Acceptance criteria:** After successful password-change logout, offline navigation cannot display A's private data. Logging into B never hydrates A's state. Failed password changes preserve pending work. Multi-tab cleanup does not race with persistence.

## Confirmed: Shared

### F04 — High: Concurrent task patches overwrite unrelated fields

**Affected app:** Shared tasks.

**Locations:** `app/lib/tasks.ts:40`, `app/lib/tasks.ts:175`, `app/lib/tasks.ts:181`, `app/lib/spaces.ts:65`.

**Evidence:** `updateTask()` reads the task without locking it, merges submitted fields and then writes all task fields. `inSpace()` takes shared membership/space locks, allowing concurrent requests. Two members can read the same task, independently rename it and edit its notes, then overwrite each other's changes. The eventual UPDATE lock does not refresh values already calculated in application memory.

**Impact/trigger:** Simultaneous partial updates can silently lose unrelated changes. The actual merge function reproduced stale snapshots where the second write restored the old title. Database concurrency was not exercised because it would require writes.

**Reproduction:** In a disposable database, use barriers so two requests read the same initial task; submit a title patch and a notes patch, then let them write sequentially. Inspect both fields.

**Recommended fix:** Lock the task row before reading current state, or use optimistic version checks. Update only submitted fields where possible. Keep assignments in the same transaction and maintain a consistent lock order. Do not blindly upgrade already-held shared space locks in a way that creates deadlocks.

**Acceptance criteria:** A deterministic two-client test retains both independent field changes. Competing edits to the same field serialize or return an explicit conflict. Assignment data remains consistent.

**Reference:** [PostgreSQL 16 locking documentation](https://www.postgresql.org/docs/16/explicit-locking.html).

### F07 — Medium: Recurring completion is not replay-safe

**Affected app:** Shared recurring tasks.

**Locations:** `app/lib/task-types.ts:66`, `app/lib/tasks.ts:175`, `app/components/shared/shared-data.ts:164`.

**Evidence:** Completing a recurring task advances its due date and resets `isComplete` to false. Repeating the same `{isComplete:true}` command advances it again. The actual function produced:

```text
Original due date: 2026-11-18
First completion: 2026-11-19
Same completion replayed: 2026-11-20
```

The client also ignores the returned server task and reapplies its local calculation.

**Impact/trigger:** Uncertain delivery/replay or two members completing the same occurrence can skip an occurrence. Client/server calculations can also disagree after delayed synchronization.

**Reproduction:** Send the same completion twice for a daily recurring task. Include a test where two clients act on the same occurrence.

**Recommended fix:** Identify the occurrence being completed and introduce idempotency or expected-version checks. Reconcile the UI using the authoritative response. Coordinate with F04; an operation ID alone may not resolve two different users completing the same occurrence.

**Acceptance criteria:** Replaying one completion does not advance twice; two clients cannot accidentally complete the same occurrence twice; the next distinct occurrence remains completable; displayed and server due dates agree after synchronization.

## Confirmed: Shows, Books and Recipes

### F08 — Medium: Shows additions cannot resume after reload

**Affected app:** Shows library additions.

**Locations:** `app/components/shows/library.tsx:50`, `app/components/shows/library.tsx:121`, `app/components/common/QueryProvider.tsx:79`.

**Evidence:** `setupShows()` registers a default function for `library-change`, but not `library-add`. Adding a title uses a component-local mutation function. Paused additions are persisted, but their function cannot be serialized or recovered after reload, even when reopening Shows itself.

**Impact/trigger:** An addition queued while offline cannot complete after reload. Fixing F01 alone does not solve this missing handler.

**Reproduction:** Load a title, go offline, select Add to library, allow persistence, reload and reconnect. Inspect the restored addition.

**Recommended fix:** Register addition handling and success reconciliation in `setupShows()`. Alternatively, explicitly reject offline additions before they enter the persisted queue. Preserve ordering with changes/removals and avoid duplicate additions on replay.

**Acceptance criteria:** Reloading with a queued addition reliably completes it once, or the UI clearly refuses offline addition without leaving an unrecoverable operation. The library reconciles correctly after restored operations.

### F09 — Medium: Books is excluded from offline document caching

**Affected app:** Books.

**Locations:** `app/public/sw.js:16`, `app/components/books/books-data.tsx:72`, `docs/decisions/0019-books.md:7`.

**Evidence:** Books persists shelves for offline reading, but the service worker's navigation allowlist includes only Shared, Shows, Recipes and Fitness. Cached shelf data cannot help when a fresh offline navigation cannot load the app document.

**Impact/trigger:** Closing and reopening Books while offline does not reliably provide the documented offline reading capability.

**Reproduction:** Visit Books in production mode, close the tab, disable networking and reopen `/books` or a previously visited shelf view. The production service-worker flow was not tested with an authenticated account during the audit.

**Recommended fix:** Add intended Books document routes, subject to F03's account isolation. Do not indiscriminately cache friends' private profile documents.

**Acceptance criteria:** Previously visited Books shelf views reopen offline with the correct account's data. Uncached views fail clearly; private profile access is not widened.

### F06 — Medium: Recipe uploads exceed the framework's buffering limit

**Affected app:** Recipes photo uploads.

**Locations:** `app/lib/recipe-photos.ts:21`, `app/app/api/recipes/[id]/photos/route.ts:30`, `app/proxy.ts:31`, `app/next.config.ts:3`.

**Evidence:** Recipes accepts files up to 20 MiB and nginx permits 21 MB request bodies. The route passes through Next.js Proxy without an `experimental.proxyClientMaxBodySize` override. Installed Next.js defaults to 10 MiB. A direct safe test of its body-cloning implementation buffered 10,485,760 bytes from a 12,582,912-byte input. Truncated multipart data then reaches `request.formData()`.

**Impact/trigger:** Valid photos between the proxy limit and the advertised upload limit fail, potentially with a misleading malformed-file message. This finding applies specifically to the proxied recipe route; do not assume the avatar route has identical proxy coverage.

**Reproduction:** Upload a valid 12–19 MiB photo to a recipe through an isolated nginx/Next.js stack.

**Recommended fix:** Align the proxy buffer with the accepted multipart size, including overhead, or lower the advertised limit consistently. Retain edge and handler limits and consider concurrent upload memory use.

**Acceptance criteria:** Valid files below the advertised limit succeed through nginx and Next.js. Oversized files receive a clear 413. Malformed multipart requests remain rejected.

**Reference:** [Next.js proxy body limit documentation](https://nextjs.org/docs/app/api-reference/config/next-config-js/proxyClientMaxBodySize). The audit also checked bundled documentation and implementation for installed Next.js 16.4.5.

## Confirmed: testing, deployment and operations

### F05 — High: E2E cleanup can delete legitimate data

**Affected component:** test database and media lifecycle.

**Locations:** `app/e2e/db.ts:7`, `app/e2e/global-teardown.ts:15`, `app/e2e/global-teardown.ts:33`, `app/lib/account-rules.ts:45`.

**Evidence:** Tests fall back to the normal `.env.local` database. Teardown deletes every user whose username starts with `e2e_`, their media and spaces owned by those accounts. That prefix is valid for ordinary registrations. Cleanup predicates are not restricted to records created by the current run.

**Impact/trigger:** A legitimate `e2e_…` account can be deleted by a test run. Deleting an owned space also deletes calendar/task data shared with other members. Concurrent test runs can affect each other's fixtures.

**Verification:** Static inspection establishes the unguarded connection and broad DELETE predicates. Cleanup was intentionally not executed.

**Recommended fix:** Require an explicitly designated disposable test database and separate media directories. Reject ordinary application databases. Track exact records created by the current run rather than treating a username prefix as ownership proof. Do not merely reserve the prefix and leave dangerous database targeting unchanged.

**Acceptance criteria:** Tests refuse to start against a non-test database. Cleanup leaves preexisting users, including `e2e_…` users, and their spaces untouched. Concurrent runs cannot delete each other's fixtures. Test media never shares the application directory.

### F10 — Medium: Logs retain bearer secrets

**Affected component:** nginx logging and token-bearing routes.

**Locations:** `nginx/nginx.conf:18`, `nginx/nginx.conf:173`, `app/lib/calendar-feeds.ts:20`, `app/auth.ts:125`.

**Evidence:** nginx uses its default access-log format, recording the request URI. Calendar URLs contain long-lived bearer tokens in the path; password-reset links contain tokens in the query. These values enter container logs even though the application protects them elsewhere. Production logs were not inspected.

**Impact/trigger:** A recipient of relevant logs can obtain calendar access until rotation, or use an unexpired authentication link. Token lifetime and whether the link has already been consumed affect authentication-link exposure.

**Reproduction:** In an isolated nginx stack, request synthetic calendar-token paths and reset-token queries and inspect logs. Never use real tokens for this test.

**Recommended fix:** Add sanitized log formatting/path mapping. Redact token path segments and omit sensitive query strings and referrers. Check error/rate-limit logs too. Preserve useful nonsecret diagnostics.

**Acceptance criteria:** Synthetic tokens never appear in any configured log stream, while method, sanitized route, status and useful timing remain available.

**Reference:** [nginx logging documentation](https://nginx.org/en/docs/http/ngx_http_log_module.html).

### F11 — Medium: Skipped media backups still trigger retention deletion

**Affected component:** backup retention for avatars and recipe photos.

**Locations:** `infra/backup.sh:43`, `infra/backup.sh:52`, `infra/backup.sh:59`.

**Evidence:** If the application container is unavailable, media archiving is skipped successfully. After a successful database dump, the common retention command still deletes old avatar and recipe-photo archives.

**Impact/trigger:** Skipped media backups do not preserve their last good archive. A prolonged app outage or missing media mount can age out all recoverable media copies.

**Reproduction:** In a disposable fixture, provide aged media archives, make the database dump succeed and make the app-directory check fail. Inspect retention selections; do not run this against real backup directories.

**Recommended fix:** Track success independently for database, avatars and recipe photos. Prune a category only after a verified replacement exists and preserve at least one known-good archive. Prefer reading the volume independently of app availability.

**Acceptance criteria:** Skipping/failing media backup preserves old media archives and reports degraded backup status. Successful categories retain normal retention behavior.

### F12 — Medium: Full behavioral tests are bypassed by the normal workflow

**Affected component:** CI and production-only regression coverage.

**Locations:** `.github/workflows/deploy.yml:37`, `.github/workflows/ci.yml:72`, `app/playwright.config.ts:61`, `app/components/common/OfflineSupport.tsx:12`, `docs/decisions/0015-only-main.md:7`.

**Evidence:** The documented workflow commits directly to `main`. Deploys run only `views.spec.ts` and `auth.spec.ts`; the complete suite runs on pull requests, which the normal workflow does not use. All browser tests run `next dev`, disabling the production service worker. No full-suite production-service-worker job is configured.

**Impact/trigger:** App-specific behavioral regressions can deploy without their existing tests running automatically. Production offline document behavior is outside the current browser suite.

**Verification:** Inspect workflow inputs and resulting test-file selection. This is a coverage gap, not a claim that every omitted test currently fails.

**Recommended fix:** Preserve the main-only workflow if desired, but add an automatic full-suite run at an appropriate gate or schedule. Add a small production-build suite for offline persistence, account transitions and upload boundaries. Resolve F05 first. A scheduled run detects regressions after deployment; a deployment gate prevents them, so document the chosen tradeoff.

**Acceptance criteria:** Normal main-only development automatically exercises the complete behavioral suite. A production-mode suite registers the service worker and detects F01–F03/F09 regressions. Tests use isolated resources.

## Suspected issues: investigate before implementing

### S01 — Medium: Concurrent Benfica imports may create duplicate events

**Affected app:** Shared calendar import.

**Locations:** `app/lib/events.ts:144`, `app/lib/events.ts:155`, `app/app/api/shared/import/benfica/route.ts:8`.

**Evidence/risk:** Import checks for an existing title/kickoff and then inserts under shared space locks. Two members may both pass the existence check and insert duplicates. No concurrent database reproduction was run.

**Verification:** Synchronize two imports at the existence check in a disposable database; count events per fixture.

**Conditional fix:** Serialize imports or store a provider fixture identity with a space-scoped uniqueness constraint. Do not make all manually created event titles/times unique. Any schema change must be additive and rollback-compatible.

**Acceptance criteria:** Concurrent imports create one event per fixture with accurate added/skipped counts. Manual events remain unrestricted by provider-specific deduplication.

### S02 — Medium: Export and feed reads may cross membership changes

**Affected components:** account export and Shared calendar subscription.

**Locations:** `app/app/api/account/export/route.ts:55`, `app/app/api/account/export/route.ts:63`, `app/lib/calendar-feeds.ts:57`.

**Evidence/risk:** Export reads membership in one transaction and later reads space data in another. Feed reads omit the membership locks used by normal Shared operations. Departure between these steps may allow an in-flight response to include subsequent changes in the old space.

**Verification:** Pause after membership lookup, complete departure, create a new event, then resume the read. Decide and document the intended authorization boundary.

**Conditional fix:** Authorize and read under one consistent membership-protected transaction, without unnecessarily locking across external requests.

**Acceptance criteria:** Responses cannot include changes made after access was revoked under the documented authorization boundary. Tests cover both export and subscription requests.

### S03 — Medium: Failed account deletion may leave partially deleted data

**Affected component:** account deletion.

**Location:** `app/auth.ts:64`.

**Evidence/risk:** `beforeDelete` leaves the user's space and removes media before Better Auth deletes the account. These actions span separate transactions and filesystem operations. A later failure may leave the account present after destructive cleanup; a last member's space may already be gone. Failure injection was not performed.

**Verification:** Inject failures after leaving the space and during media removal in an isolated environment. Inspect the installed Better Auth deletion lifecycle before designing changes.

**Conditional fix:** Make database deletion changes atomic where feasible; use durable, retryable post-commit file cleanup. Filesystem and database operations cannot simply be assumed to share a transaction.

**Acceptance criteria:** Failure preserves the account's logical data or leaves an explicit, recoverable deletion job rather than unexplained partial deletion. Retrying cleanup is safe.

### S04 — Low: Dataset growth may undermine offline persistence

**Affected apps:** especially Fitness and Recipes; shared persistence.

**Locations:** `app/lib/fitness.ts:53`, `app/lib/recipes.ts:27`, `app/components/common/QueryProvider.tsx:66`.

**Evidence/risk:** Fitness loads complete history, Recipes loads complete recipe text, and successful results are serialized into localStorage. Latency, memory use and storage-quota headroom were not measured. The intended small user population does not by itself establish per-user dataset size.

**Verification:** Use representative multi-year datasets; measure response size, render time, serialization/persistence time and quota failure behavior.

**Conditional fix:** Introduce bounded reads or more suitable storage only where measurements justify it. Surface persistence failure and protect pending operations; do not add pagination solely as a stylistic preference.

**Acceptance criteria:** Supported dataset sizes meet agreed performance targets. Storage failures never falsely imply that unsynchronized work is safely persisted.

## Dependency-aware remediation sequence

1. **F05: make testing safe.** Establish disposable databases and media directories before running mutating regression suites.
2. **F01 + F02 + F08: protect pending offline operations.** Design storage boundaries, operation handlers and migration together. Ensure deployment of the fix itself does not erase existing queued work.
3. **F03: close the local privacy gap.** Integrate successful account-transition cleanup with the persistence design, including other tabs and in-flight persistence.
4. **F04, then F07: correct Shared write semantics.** Establish locking/version rules, then occurrence-aware completion and idempotency. Investigate S01/S02 with the concurrency harness.
5. **F06 + F09: fix bounded integration defects.** Align upload limits and add Books offline routes after account isolation is addressed.
6. **F10 + F11: harden operations.** Sanitize logs, protect valid media backups and investigate S03 with failure injection.
7. **F12: automate regression verification.** Integrate full behavioral and production-mode suites into the actual main-only workflow. Build the test harness earlier as needed for preceding fixes.
8. **S04: measure before optimizing.** Do not add speculative pagination, caching or dependency upgrades without evidence.

### Dependency audit interpretation

The five reported high entries were `picomatch`, `fdir`, `tinyglobby`, `vite` and `vitest`, all rooted in `GHSA-fc5q-39xc-vjpf`. GitHub marked the advisory withdrawn on the audit date. The installed dependency tree showed Vitest reachable through Better Auth, even with development dependencies omitted; this does not establish inclusion in the final traced standalone image or an exploitable production path.

Do not mechanically apply the audit's proposed major Vitest downgrade. Recheck advisory status, dependency reachability and actual image contents before changing dependencies.

Reference: [GitHub advisory GHSA-fc5q-39xc-vjpf](https://github.com/advisories/GHSA-fc5q-39xc-vjpf).

### Positive controls observed

Parameterized queries, user/space ownership checks, mutation-origin validation, bounded schemas, processed uploads, authentication rate limits, protected production test hooks, private production database networking, pinned workflow actions, rotated container logs and documented recovery procedures were present. Public pages have titles/canonical metadata; private app and authentication pages declare no-index behavior.

Intentional choices were not treated as defects: open sign-up with usable unverified accounts, local in-memory limits at the documented small single-process scale, main-only development itself, legacy schema retained for rollback, and optional offsite backup.
