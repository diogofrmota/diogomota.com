# diogomota.com

Personal site plus two small apps for friends (Shared, Shows), built with Next.js and PostgreSQL. The spec and the full build log are in [plan.md](plan.md), the decisions one by one in [docs/decisions/](docs/decisions/), what each version changed in [CHANGELOG.md](CHANGELOG.md); running the server is in [docs/operations.md](docs/operations.md). The Playwright tests (`app/e2e/`) are the detailed spec of what the apps do; this file says it in words.

## Prerequisites

- Node.js 24
- Docker Desktop (with Compose)

## Local setup

1. `cp .env.example .env` and fill in the values. Docker Compose reads this file.
2. Create `app/.env.local` with the app variables from `.env` (at least `DATABASE_URL`, `AUTH_SECRET` and `AUTH_URL=http://localhost:3000`, and `TMDB_READ_TOKEN` for real data in the Shows app). Next.js and `npm run migrate` read this file. With `RESEND_API_KEY` and `MAIL_FROM` set, the emails (password resets, the links that confirm an email) are really sent; without `RESEND_API_KEY`, the dev server prints them (and their link) to its console instead.
3. `docker compose up -d` starts Postgres 16 on `localhost:5432`. Wait until `docker compose ps` shows it as healthy.
4. `cd app && npm ci && npm run migrate`
5. `npm run dev`, then open http://localhost:3000 (the health check is at `/api/health`).

Before your first e2e run, install the test browser with `npx playwright install chromium`. To start over with an empty database, run `docker compose down -v`.

## Migrations

Add a new file `db/migrations/NNN_name.sql`, and never edit one that has already been applied. Each file runs in its own transaction, and applied files are recorded in `schema_migrations`.

Migrations **expand and contract**. `deploy.sh` applies a release's migrations while the previous release is still serving, and a rollback runs an older image on the current schema, so a migration only adds what its release needs. Taking something away (dropping or renaming a column or table, changing a column's type, making a column NOT NULL) waits for a later release, once no deployed image uses it, and says so in a comment: `-- contract: events.notes, unread since v1.2.0`. `npm run check:migrations` (in CI) refuses a migration from `015` on that takes something away without one. Waiting now: `events.notes`, `users.password_hash` and `password_changed_at` (with the `accounts_sync_password` trigger), `password_resets`, `user_shows.rating`.

## Design system

The apps and the pages around them (`/apps`, `/account`, `/privacy`, the login pages) take their colors from the user's theme, Light or Dark ([components/common/themes.module.css](app/components/common/themes.module.css), each with its own accent; [lib/themes.ts](app/lib/themes.ts) shows Light for a theme id it doesn't know), and every size from one set of scales on the app shell ([components/common/AppShell.module.css](app/components/common/AppShell.module.css)): corners (`--radius-xs` to `--radius-xl`), text (`--text-2xs` to `--text-3xl`, three weights), spacing (4 px steps), shadows and motion. A rounded box inside another, close to its edge, has the outer radius less the room between them. The common parts are components, [components/common/ui.tsx](app/components/common/ui.tsx) (`Button` and its variants `primary`, `remove`, `danger` and `quiet`, `Alert` with Retry or ×, `Notice`, `Confirm`, `SrOnly`), on [components/common/ui.module.css](app/components/common/ui.module.css) (headings, cards, fields); the variants are on `.button` (two classes), so they win over an app's own rules for the buttons in its views, and the apps keep no copies of them. Undo is one component too ([components/common/Undo.tsx](app/components/common/Undo.tsx)): a message at the bottom of the screen (over the tab bar on a phone) with Undo for 5 seconds, paused while the pointer or focus is on it, for what is deleted or left; only what can't be undone asks first. Icons are the one line set in [components/common/icons.tsx](app/components/common/icons.tsx), with no text glyphs standing in for them. Numbers that line up or change in place use tabular figures; headings wrap into even lines. Motion is only for feedback: a message comes in from above (an error also shakes once), a pressed button gives a little, a heart or a ticked task pops (and the task then slides away into Done), the undo message rises in. All of it stops with reduced motion. The only monospace text is an invite code. On `/apps` and in its login prompt, each app has a small picture of itself ([components/site/AppPreview.tsx](app/components/site/AppPreview.tsx)), drawn in the page's theme. Log in and Sign up follow one rule everywhere: Log in first and plain, Sign up after it and filled with the accent.

## Shared spaces

`/shared` is a calendar and task lists for a couple (up to 10 people can join). It offers creating or joining a space until the user has one ("Your shared calendar"), then opens Calendar. A space has no name (`012` dropped `spaces.name`): it is its members, calendar and task lists, and creating one is a button; a space of one has Invite your partner over its calendar (Share invite link, or Not now, remembered on the device) until someone joins. Its tabs are Calendar, Tasks and Settings, each at its own URL (`/shared`, `/shared/tasks`, `/shared/settings`). Settings has the members (each with their profile picture, or initial, in a ring of their color, then their name and @username: `Diogo Mota (@diogofrmota)`), Invite someone, Calendar in your phone (see [Shared calendar](#shared-calendar)), Recent activity (what the members did lately: joined, added or changed an event, made a list, added or ticked off a task; 60 days), and Leave this group, which is done with Undo, or, as the last member, asks first (Leave and delete: the space and its data go). Each space supports up to 10 members, with distinct named colors; ownership passes by join time.

Any member invites: **Share invite link** makes a single-use link, `/join/<code>`, valid 24 hours, and opens the phone's share sheet (or copies it where there is none); the link and its 8-character code are shown, with Copy link and when it expires (`14 Nov 2026, 15:30`: Lisbon time, the 24-hour clock, the day first). The link's page ([app/join/[code]](app/app/join/[code]/page.tsx)) says who sent it ("Ana invited you to Shared"); logged out, it has Log in and Sign up, which come back to it; logged in, Join (opening it never joins, so a link preview can't); a used, expired or unknown code says so, and someone already in a space is told to leave theirs first. The code also works typed in Join space.

The authenticated JSON API is `/api/shared/spaces`, one route file per endpoint, each on `apiRoute` ([lib/http.ts](app/lib/http.ts): the session, changes only from this site, JSON bodies checked by the zod schemas of [lib/schemas.ts](app/lib/schemas.ts)): `GET` reads your space (`{id, ownerId, members}`, each member `{id, username, avatarUrl, name, color, role}`), `POST {}` creates one, and `POST /join {code}` joins. `GET /:id` reads a space, `POST /:id/invites {}` makes a code (`{code, expiresAt}`), and `POST /:id/leave {}` leaves. `GET /api/shared/activity` is the space's recent activity. Responses contain `data` or an `error` message. Reads and mutations check current database membership, inside the same transaction; another space's id answers 404. Requests lock the rows they depend on, the user's then the space's ([lib/spaces.ts](app/lib/spaces.ts)): the calendar's and tasks' share them (`FOR SHARE`), so members work at the same time and other spaces are never in the way; joining, leaving and creating take them alone (`FOR UPDATE`), so two people can't take the last place or the same color, and a member can't leave halfway through a request that assigns them something. Join attempts are limited to 20 per 15 minutes per user. Migration `004_space_membership.sql` records join times and enforces unique member colors within a space; `017` records who made an invite.

## Shared calendar

Calendar has Month and Agenda views. The agenda is the default on a phone, the month on a wide screen. One compact toolbar has Previous, the month and year, Next, a toggle to the other view, and Add event. There is no Today button, day/week view or color legend. The calendar uses the full page width, with smaller event text. A month shows two events per day, followed by "+N more", which opens the agenda from that date. Swiping the month moves to the previous or next month. The agenda shows the coming days with plans, 4 weeks at a time, with Show the next 4 weeks to extend it. Each event shows its title and the assigned members' pictures (or initials); its times and full assignment are in its dialog and accessible label. Existing group events remain readable. New events select individual members, including everyone by selecting each person. Event dialogs are centered popups with margins at every screen size, scroll internally when needed, and have no entrance movement. Escape and browser Back close them, and an open event is in the URL.

Times are entered and displayed in `Europe/Lisbon`, regardless of the device time zone, on the 24-hour clock, and stored in PostgreSQL `timestamptz` as UTC instants. The event form, Create a new event, has the Event title, the dates and times, and Who?: each member's small profile picture (or initial), by their name for screen readers, **any number of them**, including everyone by selecting each member ([components/shared/MemberPicker.tsx](app/components/shared/MemberPicker.tsx)); the one adding it is chosen to start with. Events have no notes. Dates and times are typed, not the browser's fields, which follow the device's language and can show AM and PM: a date shows `dd/mm/yyyy` while empty and its blanks, `__/__/____`, once focused, which fill in as it's typed (number keys on a phone), and a time `__:__`; focused, the field is all selected, so typing starts it over. A date that isn't real (31/02) or a time past 23:59 stops the form, saying what to type. A new event starts on the day tapped (or the one shown). A day of the month shows its first two events, slim, then, when it has more, "+1 more" (and so on) in small letters, which opens the agenda at that date; on a phone its number, events and "+1 more" are tight (a 22 px number and events with up to three lines of smaller text), smaller than a finger (the whole day is there to tap too), so they fit. Where the six weeks don't have that much room, the month scrolls as a whole. The form's button is Save. On one day, a new start time moves the end time with it, keeping the event's length. Events can span dates. A tap on a day of the month adds an event that day. All-day events (`events.all_day`, from `011`) run from the start of their first day to the start of the day after their last, show as All day in the agenda, and export as whole days. Nonexistent spring-forward times are rejected; repeated autumn times offer first/second occurrence choices. Delete event closes it with Undo. Only the days shown are loaded, and each period loaded stays (in memory, and in the browser for offline use) while the next one loads.

Exports: per event, from the event's dialog, Export to Google Calendar and an `.ics` download, each saying who it's for; and the whole calendar as a **subscription**, from Settings, Calendar in your phone: one secret link per user, `/api/calendar/<token>` ([lib/calendar-feeds.ts](app/lib/calendar-feeds.ts)), the space's events from 3 months ago on, which Google, Apple or Outlook Calendar check every few hours (Add to my calendar opens it as `webcal:`; Copy link for Google's From URL), with that app's own reminders. Whoever has the link reads the calendar; Make a new link (which asks first) stops the old one. The files use UTC timestamps, escaped text, CRLF and UTF-8 line folding per [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545).

`/api/shared/events`: `GET` lists your space's events (`?from=&to=`, UTC instants at most 400 days apart: those overlapping the range), `POST` creates one; `GET /:id`, `PATCH /:id` and `DELETE /:id` read, replace and delete an event. Create/replace accepts `{title, startsAt, endsAt, allDay, isGroup, assigneeIds}`; timestamps must be ISO UTC strings ending in `Z`, end must follow start, an all-day event runs from midnight to midnight, and a group event has no `assigneeIds` while any other has one or more current members. All space members can manage events. `GET /:id/export` downloads an event as `.ics`; `GET /api/shared/calendar-feed` answers with your subscription link (`{url, webcal}`, made the first time), and `POST` makes a new one. Every operation checks current membership inside the same transaction as the read/write. A departing member is taken off their events; an event left for nobody is labeled Former member until reassigned; they cannot access their previous space. `events.notes` stays, unread, until a contract migration.

## Shared tasks

Tasks, titled Tasks, holds any number of lists per space, shown as chips above the open list; the last list opened is remembered on the device. The open list's name has how many tasks are left to do after it, `Groceries (3)`, and new tasks are written in Write a task under it. Edit (or New list) creates, renames, reorders and deletes lists; deleting a list shows it as deleted in its row, with Undo, for 5 seconds, and then deletes it with its tasks (closing Edit deletes it at once). A task has a title, an optional due date, notes and **Repeat** (Every day, week, month or year), and zero or more assigned members, shown as small profile pictures. Its dialog (a tap on the task) has the title, then Extra options: Who?, Due date, Repeat?, and Notes, followed by Save and Delete. Who? uses the same individual checkboxes as events, with no All shortcut; its × closes it without saving. A task ticked off stays where it is for a moment, ticked and crossed out (it no longer counts as one to do), then fades and slides away into a collapsed Done section, 650 ms in all (`tickedMs` in [useTasks.ts](app/components/shared/useTasks.ts)); a **repeating** one comes back instead, unticked, with its next due date: a period after the last, skipping the ones already past (bins due on Monday and done on Tuesday are due next Monday; a month from the 31st is the end of a shorter month; `nextDue` in [lib/task-types.ts](app/lib/task-types.ts)). The change is only sent then, so unticking it in that moment leaves it as it was; leaving the Tasks view or the page sends it at once. Unticking a task in Done puts it back at the end of the list. Due dates are plain calendar dates, compared with today in `Europe/Lisbon`, typed in the task's dialog as `dd/mm/yyyy` (the event form's date field, [components/shared/MaskedField.tsx](app/components/shared/MaskedField.tsx); not the browser's, which can be `mm/dd/yyyy`), and cleared with Clear. New tasks are entered immediately below the list title, before all existing tasks. Task and list dialogs stay within the viewport with visible margins on phones.

Drag a task (or, in Edit lists, a list) by its handle to reorder it: with a mouse, a finger (the rest of the row still scrolls the page), or the keyboard (Space or Enter to pick it up, the arrow keys, Space or Enter to drop it, Escape to cancel; each step is announced to screen readers). Delete a task with its bin button where there is a mouse, by swiping it left on a touch screen, or from its dialog. Undo is offered for 5 seconds (paused while the pointer or focus is on it), and the delete is only sent once that runs out, or when you leave the Tasks view or the page.

Changes show at once and are sent one at a time, in the order they were made (TanStack Query, [components/shared/shared-data.ts](app/components/shared/shared-data.ts): each change is plain data, applied on screen on top of what the server last sent). If the server refuses one, it is undone on screen with a message saying why; when the reason is that someone else changed the list meanwhile, Tasks reloads. Without a connection, the changes show at once, a note says they wait, and they go out in order once it's back, after a reload too. While Tasks is open it loads again every 5 seconds (and when the browser tab comes back into view), so what the other member ticks off in the shop shows up.

`/api/shared/tasks`: `GET` returns every list of your space with its tasks, both in order. `POST /lists {id?, name}` adds a list at the end, `PATCH /lists/:id {name}` renames it, `DELETE /lists/:id` deletes it with its tasks, and `POST /lists/:id/move {beforeId}` moves it before another list (`null`: to the end). `POST /lists/:id/tasks {id?, title, notes?, dueDate?, assigneeIds?, isComplete?, repeat?}` adds a task at the end of a list; `PATCH /:id` changes any of those fields of a task (ticking off a repeating one moves its due date on instead), `DELETE /:id` deletes it, and `POST /:id/move {beforeId}` moves it before another task of the same list. Ids are UUIDs, and clients may choose the ids of what they create (one already in use is a 409), so later changes can refer to a list or task before its response arrives. List names are 1–80 characters, titles 1–200, notes up to 10,000; `dueDate` is `YYYY-MM-DD` or `null`; `assigneeIds` is an array of up to ten current members (empty for no assignment); legacy `assigneeId` is supported for cached clients and rollback; `repeat` is `daily`, `weekly`, `monthly`, `yearly` or `null` (`018`). Every operation checks current membership inside the same transaction as the read/write, and another space's lists and tasks answer 404. A member who leaves loses their assignments.

## Shows: TMDB and Discover

Discover (`/shows/discover`) has a TV Shows | Movies switch, remembered on the device, over sections, each one row of up to 20 cards that scrolls sideways: a swipe on a touch screen (the cards snap into place, and the next one peeks in), and with a mouse a drag, a trackpad's sideways scroll or the ‹ › buttons that show over the row's ends while the pointer is on it (only towards more); the end with more to see fades out, and the keyboard goes from card to card. A section loads once it comes near the screen (a screen's height away), so opening Discover on a phone loads what is seen first. In this order: Recommended by Friends (what friends recommended to you, each card saying who from, `From Ana`, until it's in your library; only when there is something), For You (only with titles of that type in the library: TMDB's recommendations for up to 5 of them, favourites, then completed and watching ones first, merged so a title recommended for several or near the top comes first, without the titles already in the library or in Trending and Popular), Trending This Week, Popular, for movies Coming Soon (upcoming), Top Rated (TMDB's discover sorted by rating, from titles with at least 500 votes for TV and 2,000 for movies), three genres (TV: Comedy, Crime, Sci-Fi & Fantasy; movies: Action, Comedy, Science Fiction; each the most popular of the genre) and Added by Friends (titles in the libraries of accepted friends, any status, the ones most friends have first; see [Shows: Profile and friends](#shows-profile-and-friends)). Every section from TMDB leaves out titles with fewer than 50 votes (TV) or 100 (movies), so a handful of 10s can't put something hardly anyone has seen at the top (Coming Soon's titles aren't out yet, so they need none). A title is shown only once, in the first section it would be in, in the order Trending, Popular, Coming Soon, then the genres; Top Rated and Added by Friends repeat what they like. The next pages of TMDB's list (up to 3) fill the places of the titles left out, so each section has 20. For You loads again after the library changes. Cards show the poster, title, year and TMDB's average rating, and a title in the library that is Watching or Completed says so at the poster's top left (as everywhere a poster is). The search field at the top of Discover (and Search on an empty Library), centered over the TV Shows | Movies switch, opens the search panel (the whole screen on a phone): it searches TV shows and movies together, 300 ms after typing stops, the exact title first, then titles that start with what was typed, and in each the ones with a poster and enough votes (50 for TV, 100 for movies) first. A card opens the detail panel (see [Shows: Library](#shows-library)). A + at the bottom right of every Discover and search poster ([components/shows/AddToLibrary.tsx](app/components/shows/AddToLibrary.tsx)) opens Planned, Watching and Completed over the poster, each its icon and name in the middle of a pill; Watching a TV show then asks, over the poster, the last episode watched (Season and Episode, the first one to start with, and Save; leaving it with Escape or a tap elsewhere keeps it Not started). Once the title is in the library the + is a tick, which opens its quick actions. Loading sections show grey skeleton posters; a failure shows a message with Retry. At the bottom of Discover and of a title's panel, TMDB's logo (linking to TMDB) and "This product uses the TMDB API but is not endorsed or certified by TMDB." ([components/shows/TmdbAttribution.tsx](app/components/shows/TmdbAttribution.tsx)), as [their terms](https://www.themoviedb.org/api-terms-of-use) ask.

[app/lib/tmdb.ts](app/lib/tmdb.ts) is server-only: it sends `TMDB_READ_TOKEN` (the v4 API Read Access Token) as a Bearer token, gives up after 8 s, and checks every field of TMDB's answers. The browser only calls `/api/shows` and loads posters from `image.tmdb.org`, in TMDB's sizes from `w92` to `w780` (the closest for each width of next/image's srcset). TMDB's list pages and the sections made from them stay in memory for 10 minutes, searches for 5, a title's recommendations for 6 hours. Opening a title or adding it to a library upserts it into `shows`: title, year, poster path (in `poster_url`, e.g. `/abc.jpg`), overview, genres (up to 5 of TMDB's names, `020`), movie runtime, typical episode runtime (the latest episode's when TMDB has none), episode count of each regular season (no specials) and TMDB's rating (`vote_average`, added by `005_show_rating.sql`). A copy older than 7 days, or without genres, is fetched again the next time it is opened or added, and kept as it is if TMDB can't be reached. TMDB allows caching for at most 6 months: titles nobody opens again would keep their last copy, so loading the library also refreshes its titles older than 7 days (see [Shows: Library](#shows-library)).

The authenticated JSON API: `GET /api/shows/discover/{tv|movie}/{section}` returns a section (`recommended`, `for-you`, `trending`, `popular`, `top-rated`, `comedy`, `sci-fi`, `friends`, and `crime` for TV, `upcoming` and `action` for movies), `GET /api/shows/discover/search?q=` the TV shows and movies matching `q` (1–100 characters; people and collections are left out), `GET /api/shows/titles/{tv|movie}/{tmdbId}` a title's details with your library entry (or `null`) and `friends` (your friends who have it, `{id, username, avatarUrl, name, status}`), `GET /api/shows/titles/{tv|movie}/{tmdbId}/similar` More like this, `POST /api/shows/library {type, tmdbId, status}` adds a title as `watching`, `planned` or `completed` (201, or 409 if it is already there), and `POST /api/shows/recommendations {friendId, type, tmdbId}` recommends a title to a friend (201; 404 for someone who isn't); the rest of the library API is under [Shows: Library](#shows-library). Responses contain `data` or an `error` message; when TMDB fails they answer 502 (404 for a title TMDB doesn't have). Each user can make 240 requests a minute.

In the e2e tests no request reaches TMDB: with test hooks on, `lib/tmdb.ts` hands its requests to a fake TMDB in the same process ([app/lib/tmdb-mock.ts](app/lib/tmdb-mock.ts); `/api/test/tmdb` lists what it answered), and `e2e/fixtures.ts` answers the browser's poster requests with a placeholder. The fake's ids start above 2,100,000,000, and the teardown deletes the titles it put in `shows`.

## Shows: Library

Library (`/shows`, the first tab; it was the Watchlist, and Home before) is the user's library: a TV Shows | Movies switch, remembered on the device, over three sections, Watching, Planned and Completed, each listing the titles changed most recently first (whole rows until Show all: three rows when the grid has four columns or fewer, as on a phone, two when wider). A card shows the poster (with a heart for a favourite, and Watching or Completed at its top left, as on every poster of a title in the library; Planned only where statuses are mixed, as in Favourites, not in its own section; and, on every poster of a title Watching or Completed, a friend's too, a line along its bottom edge from the left: as long as the share of a TV show's episodes watched, none at first and half way at half of them, in the Watching badge's blue, then all the way across in the Completed badge's green once completed), the title and year, and the progress of a TV show being watched (`S2 E5`, or Not started). Users don't rate titles: the only rating is TMDB's. A library that is empty when the app opens (a new account's) shows a guide instead ([components/shows/Onboarding.tsx](app/components/shows/Onboarding.tsx)), in three numbered steps: TV shows, then movies (this week's trending and the popular ones, or a search of that kind; a tap on a poster opens Planned, Watching and Completed over it, Watching a TV show then asks the last episode watched, and the title's status again takes it out), then Watch together (Add a friend); Finish shows what was added, by status, with Go to my library. Skip ends it at any step, and so does coming back to Library from another view with titles in the library. Without it, an empty library shows "Start by discovering shows!" with Go to Discover, Search and Set up step by step (the guide again); an empty section says so, with a link to Discover. Adding a title in Discover or search shows it in Library at once.

A tap or click on a card opens the detail panel ([components/shows/TitleDialog.tsx](app/components/shows/TitleDialog.tsx); its URL has it, `?p=title:tv:1396`), laid out as the title's page, over a blurred copy of the poster: on a wide screen, the poster with the title, type, year, TMDB rating, its genres (`Drama · Mystery`) and length (seasons and episodes, or a movie's runtime) under it, in a column that stays in view, and beside it Synopsis, the overview (cut to four lines, with More and Less, when it is longer), then **Friends** (your friends who have it, each with their picture, name and how far they are: Watching, Watched it, or Wants to watch it for a favourite they planned), then what can be done with it, the seasons, **Recommend to a friend** (your friends, Send each: it shows in their Discover until they add it), **More like this** (TMDB's recommendations for people who liked it, posters in a row with a visible scrollbar), Remove from library without a divider, and TMDB's notice; on a phone the poster is small, beside the title, with the rest under both. A title not in the library has Add to Library: Planned, Watching and Completed as three tiles with their icons. One in the library has its status (Planned | Watching | Completed, with their icons, one over the other on a wide screen) and Favourite under the poster and the facts (that it is in the library is only said to screen readers), and beside them, in a panel, the progress of a TV show being watched (the last episode watched, a bar and "4 of 18 episodes watched", Next episode, which moves on to the next season after a season's last episode, then a season and an episode picker, [components/shows/EpisodePicker.tsx](app/components/shows/EpisodePicker.tsx)). Its seasons show which are watched (a tick, on the faded green of a completed title) and how far into the current one (`4 of 10 episodes`). Remove from library is at once, then says so with Undo, which adds it back as it was (status, progress, favourite), and the Add to Library tiles. Setting the progress to the last episode offers Mark as completed (or Not yet). Progress is the last episode watched, and is kept when the status changes. Quick actions, for the status (and the season and episode of a TV show being watched), open from the ⋯ button on a card where there is a mouse (it shows on hover or focus), from a right click, or from a long press (half a second) on a touch screen: a small menu beside the card on desktop, a sheet from the bottom on a phone. Back or Escape closes either.

Changes show at once and are sent one at a time, in the order they were made (TanStack Query; [components/shows/library.tsx](app/components/shows/library.tsx)); if the server refuses one, it is undone with a message (and the library reloads after a 404 or 409, e.g. a title removed in another tab). The library loads with the app and again whenever the page becomes visible, and is kept in the browser for offline use; changes made offline wait and go out once the connection is back.

`GET /api/shows/library` returns the library, latest change first: each title's card fields and lengths (`runtime`, `episodeRuntime`, `episodesPerSeason`, for the stats) with its `library` entry (`status`, `currentSeason`, `currentEpisode`, `isFavourite`). `PATCH /api/shows/library/{tv|movie}/{tmdbId} {status?, isFavourite?, currentSeason?, currentEpisode?}` changes your entry for a title and returns it: the progress (TV only) is both fields together, an episode the show has according to its cached seasons, or both `null`. Anything else in the body is ignored, `rating` too (users used to rate titles; `user_shows.rating` keeps the old ratings, unread, so an older image still works). `DELETE` on the same path removes it from your library. Both answer 404 for a title that isn't in your library, so nobody can change anyone else's. `006_library_updated_at.sql` adds `user_shows.updated_at`, set by every add and change, for the order. Loading the library answers with the cached copies and then, after the response, fetches the titles older than 7 days from TMDB again, one at a time, stopping at the first failure. Adding a title, a new status and a new favourite go in your friends' activity feed.

## Shows: Profile and friends

Profile (`/shows/profile`) is one column in the middle of the page, every block as wide as it. From the top, in the middle: your profile picture (or initial), your name under it and your @username under that (the @username alone without a name), and nothing else; the friend requests you received, with Accept and Decline (only when there are any); Stats; Favourites (the titles marked Favourite, TV shows and movies together, latest change first, whole rows until Show all, with Library's quick actions); **Friends' activity** (what your friends started watching, planned, finished, made a favourite or recommended, newest first, 60 days; a title opens its panel; [components/common/ActivityFeed.tsx](app/components/common/ActivityFeed.tsx)); and Friends: a search field (Search friends…, named Add a friend for screen readers), which from 2 characters lists up to 6 people whose username, name or a word of their name starts with what's typed (`mota` finds `Diogo Mota`; in any case and without accents; after an `@`, usernames only), each as their picture, name and @username, `Diogo Mota (@diogofrmota)`, with how you're connected (Friends, Request sent, Sent you a request; arrows and Enter or a tap pick one, which puts their username in the field, and Escape closes the list), and says whether an account has exactly that username. Send request asks it, or with a name typed, the one person found (for several, it says to choose someone from the list). Then your friends, each a row with their picture, name and @username and Check profile, which the whole row opens, and a bin to remove them, at once with Undo (on a phone, the name and @username on one line, and Check profile and the bin under it); and the requests you sent (with Cancel). Each answer, or the reason it was refused, shows in the section it was made in; when the button pressed goes away with its row, focus moves to that message. Friend requests and answers apply to both people at once; the other person sees them the next time their Profile loads, which it does whenever it is shown and when the page becomes visible again.

Stats: TV shows completed and movies completed on the first row, then hours watched below them. Hours watched is each TV show's episodes watched times its episode runtime, plus the runtime of each completed movie, rounded to one decimal. A show being watched counts up to its current episode included (S2 E5 after a first season of 10 is 15 episodes), a completed show all of its episodes, a planned one none (even with progress from before); a movie counts once completed. Runtimes are TMDB's, from the `shows` cache; a title without one counts 0 minutes. Your own stats follow every change at once: the browser works them out from the library with `libraryStats` ([app/lib/show-types.ts](app/lib/show-types.ts)), the same function the server uses for a friend's.

A friend's row opens their profile (the whole screen on a phone, `?p=friend:<id>`; Back or Escape closes it), read-only: their stats, Watching, Completed, Favourites, and **You both want to watch** (the titles you've both planned). Planned titles that aren't favourites are left out, of the API answer too. A card opens the title's detail panel on top, about your own library, so you can add it. Added by Friends in Discover loads again, when it is next shown, after Profile sees your friends change.

Friendships use the `friendships` table from `001_initial.sql`: one row per pair of users, `user_id` sent the request. It is pending until the other person accepts; declining, cancelling and removing delete the row, so either of them can ask again later. Asking someone who has already asked you accepts their request (in one statement, so two people asking each other at once become friends).

The authenticated JSON API, under the same rules as the rest of `/api/shows` (changes only from this site, JSON bodies, 240 requests a minute per user): `GET /api/shows/friends` returns `{friends, incoming, outgoing}`, each a list of `{id, username, avatarUrl, name}` by username (`avatarUrl` is their profile picture, or `null`, and `name` `null` until they set one; everywhere a person is shown, so are they). `GET /api/shows/friends/search?q=` returns `{matches, exact, self}`: up to 6 people as above with their `relation` (`none`, `friend`, `incoming`, `outgoing`), whose username, name or a word of their name starts with `q` (2–50 characters, spaces tidied; names compared in lowercase and without accents, with `013`'s `unaccent`; after an `@`, only usernames, so only a-z, 0-9 and _; anything else answers no matches), the exact username first, then the other usernames, then names, never yourself; whether another account has exactly `q` as its username, and whether it is yours; 60 searches a minute per user. Usernames are served by `010`'s prefix index on `users.username`; names have no index (there are a handful of accounts). `POST /api/shows/friends {username}` sends a request, or accepts theirs (201); it answers 400 for an empty or impossible username or your own, 404 when no account has it, 409 when you are friends already or have already asked, and 429 after 20 requests in 15 minutes, because each answer tells whether a username exists. `POST /api/shows/friends/{userId}/accept` and `/decline` answer a request they sent you, `/cancel` withdraws one you sent (each with `{}`), and `DELETE /api/shows/friends/{userId}` removes a friend for both of you; these answer with the new `{friends, incoming, outgoing}`, or 404 when there is no such request or friendship. `GET /api/shows/friends/{userId}` returns a friend's profile: `{id, username, avatarUrl, name, stats, items, bothPlanned}`, where `stats` is `{tvCompleted, moviesCompleted, episodesWatched, minutesWatched}`, `items` their watching and completed titles and favourites, latest change first, each with its `episodesPerSeason` (for the progress line) and `library: {status, currentSeason, currentEpisode, isFavourite}` (no entry ids), and `bothPlanned` the titles you've both planned. Anyone who isn't an accepted friend (a pending request, a stranger, yourself, an id nobody has) gets 404, "Only friends can see each other's libraries." `GET /api/shows/activity` is your friends' recent activity.

## Accounts, email and profile pictures

Accounts are [Better Auth](https://www.better-auth.com) ([app/auth.ts](app/auth.ts)) on the site's own tables (`016_better_auth.sql`): `users`, `accounts` (each password's bcrypt hash, [lib/password.ts](app/lib/password.ts), so passwords from before still work), `sessions` (read on every request, so logging out, a password change and deleting the account end them at once) and `verifications` (reset tokens, only their SHA-256). The forms are server actions that check their fields and rate limits and then call `auth.api`; Better Auth's same operations over HTTP are switched off (`disabledPaths`), so nothing gets around those checks. `/api/auth/*` serves the links in emails and the session. `getSession()` and `requireUser()` (in `auth.ts`) are how pages, actions and routes read the user.

Signing up sends a link to confirm the email (24 hours, [lib/auth-emails.ts](app/lib/auth-emails.ts)); until it's opened, `/apps` and `/account` say so (Send the link again, 3 an hour), and password resets don't go to that email. Accounts from before email confirmation count as confirmed. Changing the email in `/account` takes the current password and sends a link to the new address; the email only changes once it is opened (`Your email is changed.`), and an address another account has gets the same answer, and nothing.

`/account` has the profile picture in the middle (a pencil on it says it can be changed), then a row each for Name, Username, Email (with `(not confirmed)` until it is) and Theme with what they are now, then Update password and Log out, then **Your data**: Download my data (`GET /api/account/export`, a JSON file: the account, the Shows library, friends and recommendations, the activity, and the space's members, calendar and tasks; not the password or sessions) and Delete my account (a popup that takes the password: it leaves the space, which goes with its last member, deletes the profile picture's file, and everything else goes with the account; then `/apps` says it's done). [/privacy](app/app/privacy/page.tsx) says what is kept, why, and who else sees it. Each row opens a popup with its form ([components/account/AccountSettings.tsx](app/components/account/AccountSettings.tsx)); Escape, a click outside or its × close it, and once saved it closes and says so under the rows. Name is one field, as sign-up has, for the name as the user wants it, `Diogo` or `Diogo Mota`: up to 50 characters, kept as typed but trimmed, with one space between words. `014_one_name.sql` made it `users.name`; accounts made before names have none until they set one, and show as their @username alone. Both apps show it with the @username, `Diogo Mota (@diogofrmota)` ([components/common/PersonName.tsx](app/components/common/PersonName.tsx)). Theme is Light or Dark. Profile picture ([AvatarForm](app/components/account/AccountSettings.tsx)) shows the picture there is (or the username's initial) and a drop zone: a photo dragged onto it, or one chosen with a click or tap (the file picker; on a phone, the photos or the camera), opens Adjust your picture ([AvatarCrop](app/components/account/AvatarCrop.tsx)): the photo in a square with the circle that is kept marked on it, to drag (a finger, the mouse, or the arrow keys) and zoom (the slider with − and +, the mouse wheel, a pinch, or + and −). Save picture cuts that square out in the browser (a canvas, at most 1,024 px a side, WebP, or PNG where the browser can't make WebP) and sends it; it shows in the circle under a spinner until it's saved. Cancel, Escape or a click outside sends nothing. A photo the browser can't show (HEIC; TIFF outside Safari) is sent as it is, and the server decides. The account menu then has it on every page, as do Shared's members and Shows' Profile and friends. Remove picture goes back to the initial.

The server makes every picture small, though not much (a few friends use the site): [lib/avatars.ts](app/lib/avatars.ts) turns it upright as its EXIF says, cuts a square around what stands out in it (sharp's `attention` crop; a picture adjusted in the browser is already square), makes it 512 px a side and saves it as WebP at quality 82, without its metadata (such as where it was taken): 20–60 KB from a photo of several megabytes. Files up to 20 MB (`AVATAR_MAX_BYTES` in [lib/account-rules.ts](app/lib/account-rules.ts)) and 70 megapixels are taken, of any kind sharp reads (JPEG, PNG, WebP, GIF, AVIF, TIFF; not HEIC, which iPhones turn into JPEG when a photo is picked); 20 uploads per 15 minutes per user.

Each picture is a file, `AVATAR_DIR/<user id>.webp`, written beside and then renamed over the old one. `AVATAR_DIR` is `/app/data/avatars` in the image, on the `appdata` volume of [docker-compose.prod.yml](docker-compose.prod.yml), which keeps it across deploys and which [infra/backup.sh](infra/backup.sh) archives with every dump; without it (`npm run dev`) it is `app/data/avatars`, which git ignores. The database only has when it was last set, `users.avatar_updated_at` (from `012`), which is in its URL: `/api/avatars/<user id>?v=<ms>`. So a new picture is a new URL, and `GET /api/avatars/{userId}` (anyone logged in; 401 otherwise, 404 without a picture) lets browsers keep each one for a year. `POST /api/account/avatar` with a multipart form (the file as `picture`) sets yours and `DELETE` removes it; both answer `{avatarUrl}` (or an `error`) and, like the other APIs, only take changes from this site. nginx lets 21 MB through to that one path ([nginx/nginx.conf](nginx/nginx.conf)); everything else stays at 5 MB. The e2e teardown deletes the test accounts' pictures.

## Phones, URLs, offline, loading, errors and accessibility

Added to a phone's home screen (Share → Add to Home Screen on an iPhone, Install app in Chrome on Android), the site opens on `/apps` as an app of its own, without the browser's bars: [app/manifest.ts](app/app/manifest.ts) serves `/manifest.webmanifest`, linked from every page, and its icons are `app/icon.svg`'s `>_` as PNGs in `app/public/icons/` (192 and 512 px, and a full-bleed 512 px one that launchers can cut into their own shape); its splash screen is the Light theme's color, as `/apps` opens. There is no browser back button then, so every dialog has a close button; in the apps, Apps in the bottom bar goes to the launcher, where Account and Log out are in its bottom bar.

The launcher and both apps have a fixed bottom bar at every screen size and no top bar. On /apps, the bar has the user's profile picture with Account and a separate Log out button (Log in and Sign up when logged out). Shared has Calendar, Tasks, Settings (a gear icon) and Apps; Shows has Library, Discover, Profile and Apps. Apps returns to the launcher. Before Shared has a space, its bar still offers Apps. Account and authentication pages retain their header. All bottom bars keep their controls above the device's home indicator and reserve content space above them.

Each app's view and open panels are in its URL ([hooks/useAppView.ts](app/hooks/useAppView.ts), [lib/app-views.ts](app/lib/app-views.ts)): the view is the path after the app's (`/shows/discover`; the app's own path is its first view) and the panels, bottom to top, its `p` parameters (`/shows/discover?p=search&p=title:tv:1396`), so a reload keeps them and any of them can be linked to or bookmarked; a path that isn't a view is a 404. Moving between them never loads a page: each change is a `history.pushState` entry, which Next.js's router takes in, and Back closes the open panel, then goes back through the views and finally out to `/apps`. A panel that came with the URL closes by replacing its entry, so closing it never leaves the app.

Both apps' dialogs are [components/common/Dialog.tsx](app/components/common/Dialog.tsx): modal, centered with visible margins on phones, internally scrollable, and without an entrance animation, closed by Escape, Back, a tap outside them or their × button, which hands focus back to what opened them; the page behind doesn't scroll. With a mouse, a popup with a text field to fill (Account's, a new event) opens with it focused; on a touch screen it doesn't, so the keyboard doesn't come up over the popup before it's seen: a tap on the field types. On a phone, controls are at least 44x44 px, text fields have 16 px text (so iOS doesn't zoom in on them), and sheets and the undo message stay clear of the home indicator and the tab bar.

**Offline:** the browser's API calls go through TanStack Query ([components/common/QueryProvider.tsx](app/components/common/QueryProvider.tsx)), which keeps Shared's space, calendar and tasks and the Shows library in the browser (`localStorage`, per user, for a week, a new version starting afresh), so the apps open with them without a connection; changes made meanwhile wait there, and go out in order once it's back, after a reload too. In production builds a service worker ([public/sw.js](app/public/sw.js), registered by `components/common/OfflineSupport`) keeps the apps' pages (from the network, the last copy without one) and Next.js's built files. Logging out (and deleting the account) forgets all of it on that device.

Loading shows grey skeletons in Shows and a spinner in Shared. A link to another page (Log in, Sign up, Account, Switch app, Back to apps) and a form's button (Log in, Save, Log out) show a spinner from the tap until the page or the answer is there, in place of their icon or over their label. A load that fails says why, "Could not reach the server. Check your connection." when offline, with Retry; the browser's API calls all go through [lib/api-request.ts](app/lib/api-request.ts). A page that fails on the server shows [app/error.tsx](app/app/error.tsx), with Retry and Back to Apps. On `/apps`, a small ring turns beside an app's name from the tap until the app has loaded.

[e2e/views.spec.ts](app/e2e/views.spec.ts) walks through every page and every view and dialog of both apps (empty, filled and failed to load), closing each with Back, and checks each with [e2e/checks.ts](app/e2e/checks.ts): nothing scrolls sideways, at 1280x800 on the desktop project and at 390x844 and 375x812 on the mobile one, where the tap targets, text field sizes and safe area above are checked too (with an emulated home indicator); and [axe](https://github.com/dequelabs/axe-core) (`@axe-core/playwright`), in the light and the dark theme, finds nothing serious or critical. Next.js's dev tools are left out of the scan.

## Docker image

From the repo root:

```sh
docker build --build-context migrations=db/migrations -t diogomota-com ./app
```

`db/migrations` is outside `./app`, so `--build-context` is how it gets into the image. Inside a container (Node 24), `npm run migrate` applies the migrations and `node server.js` starts the app on port 3000. What the app writes while it runs (the profile pictures) goes to `/app/data`, owned by the app's user `node`: mount a volume there to keep it. The bottom of `/apps` shows the image's version, `Version dev` unless you add `--build-arg APP_VERSION=v1.2.0` (also `dev` with `npm run dev`).

## Production

The VPS runs [docker-compose.prod.yml](docker-compose.prod.yml) (Postgres, app, Nginx, Certbot) in `/opt/diogomota`. Server setup, TLS, backups and restores are scripts in [infra/](infra/). Running it day to day (health checks, restarts, rollbacks, restoring a backup with a dry run first, the optional offsite backup, rotating secrets, certificates) is in [docs/operations.md](docs/operations.md).

### Deploys

Every push to `main` runs [.github/workflows/deploy.yml](.github/workflows/deploy.yml), one run at a time:

1. **check**: in `app/`, `npm ci`, Prettier (`format:check`), lint, typecheck, `check:migrations`, the unit tests and the build; then the Playwright tests against a Postgres service, the smoke set (`views.spec.ts` and `auth.spec.ts`). This is [.github/workflows/ci.yml](.github/workflows/ci.yml), which also runs on every pull request, there with every Playwright test; a failed run keeps its HTML report for a week.
2. **image**: builds the image, scans it with Grype (anchore/scan-action: a known critical vulnerability with a fix, in its OS packages or `node_modules`, stops the deploy, and the report is in the job's log), and pushes it to Docker Hub as `diogofrmota/diogomota-com:<tag>`, `:<version>` and `:latest`. The tag is the short commit SHA, its first 7 characters; the version (see [Versions](#versions)) is also shown on `/apps`, added to the commit as a git tag, and published as a GitHub Release listing the commits since the previous version.
3. **deploy**: over SSH as `deploy`, copies `docker-compose.prod.yml`, `nginx/`, `infra/` and `db/migrations/` to `/opt/diogomota` and runs [infra/deploy.sh](infra/deploy.sh) `<tag>` there. That pulls the image, applies pending migrations, sets `IMAGE_TAG=<tag>` in `.env`, runs `docker compose up -d app nginx`, reloads nginx and deletes old app images (it keeps the deployed one and the two newest others). The job then waits up to 60 s for https://diogomota.com/api/health to return 200; if it doesn't, the run fails and prints the app's logs.

The app container is replaced in place, so expect a few seconds of 502s. Apart from `IMAGE_TAG`, the deploy never touches `.env`, `backups/` or `logs/` on the VPS. A changed `infra/crontab` is copied but not installed: run `crontab infra/crontab` there.

[.github/dependabot.yml](.github/dependabot.yml) opens a pull request every Monday for each of the app's npm packages, the GitHub Actions (pinned by commit SHA, so they never move on their own) and the Docker images of the Dockerfile and the compose files, each grouped, a new version only once it's a week old (fresh releases are where supply-chain attacks land), Postgres only within its major version; CI checks each one before it is merged. nginx also limits, per client address, the form submissions of the login, sign-up, reset and join pages and `/api/auth/*` (20 a minute) and the calendar subscriptions (30 a minute), which hold across deploys, unlike the app's own limits.

The workflow needs these repository secrets (Settings → Secrets and variables → Actions): `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN` (read & write), `VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY` and `VPS_KNOWN_HOSTS`. GitHub masks secret values in logs, so the Docker Hub username, the VPS address and the word `deploy` show up as `***`.

### Versions

Every deploy gets the next patch version, `vX.Y.Z`. `app/package.json` holds `X.Y.0`, and the image job sets the patch to one more than the newest `vX.Y.*` git tag (`0` if there is none yet). To move to a new minor (or major), e.g. when a new piece of work starts (see plan.md, Build log), run `npm version 1.1.0 --no-git-tag-version` in `app/` and commit: the next deploy is `v1.1.0`, then `v1.1.1`, and so on. A version other than `X.Y.0` in `package.json` fails the image job.

A failed build doesn't use up a number, because the git tag is only added once the image is on Docker Hub. Run `git fetch --tags` to get the tags locally.

### Rollback

GitHub → Actions → Deploy → Run workflow, on `main`, with `image_tag` set to the 7-character short SHA of an older commit (`git log --oneline`, the tags on Docker Hub, or `git rev-parse --short v0.6.3` for a version). This skips check and image and deploys that existing image, using the compose, nginx and infra files of the current `main`. Migrations only go forward and are never undone, so the older image has to work with the current schema.

The rollback holds until the next push to `main`, or a run with an empty `image_tag`, which deploys the newest commit again. Without GitHub, the same thing works by hand: `ssh deploy@162.19.252.190`, then `bash /opt/diogomota/infra/deploy.sh <tag>`. To see which tag is live, check the summary of the last Deploy run, or run `grep IMAGE_TAG /opt/diogomota/.env` on the VPS.

### Logs

- **Deploys**: GitHub → Actions → Deploy → the run. The summary shows the deployed tag.
- **Containers**: on the VPS, in `/opt/diogomota`: `docker compose ps` for status and health, `docker compose logs -f app` (or `nginx`, `postgres`). Docker keeps up to 3 × 10 MB of logs per container.
- **Cron jobs**: `/opt/diogomota/logs/backup.log` and `/opt/diogomota/logs/renew-cert.log`.
