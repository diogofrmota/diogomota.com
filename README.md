# diogomota.com

Personal site plus five small apps for friends (Shared, Shows, Recipes, Fitness, Books), built with Next.js and PostgreSQL. The spec and the full build log are in [plan.md](plan.md), the decisions one by one in [docs/decisions/](docs/decisions/), what each version changed in [CHANGELOG.md](CHANGELOG.md); running the server is in [docs/operations.md](docs/operations.md). The Playwright tests (`app/e2e/`) are the detailed spec of what the apps do; this file says it in words.

## Prerequisites

- Node.js 24
- Docker Desktop (with Compose)

## Local setup

1. `cp .env.example .env` and fill in the values. Docker Compose reads this file.
2. Create `app/.env.local` with the app variables from `.env` (at least `DATABASE_URL`, `AUTH_SECRET` and `AUTH_URL=http://localhost:3000`, and `TMDB_READ_TOKEN` for real data in the Shows app). Next.js and `npm run migrate` read this file. With `RESEND_API_KEY` and `MAIL_FROM` set, the emails (password resets, the links that confirm an email) are really sent; without `RESEND_API_KEY`, the dev server prints them (and their link) to its console instead. `CONTACT_EMAIL` is where `/about`'s Get in touch form sends its messages (the address is never shown; without it, `/about` has no form and `/privacy` says to ask Diogo).
3. `docker compose up -d` starts Postgres 16 on `localhost:5432`. Wait until `docker compose ps` shows it as healthy.
4. `cd app && npm ci && npm run migrate`
5. `npm run dev`, then open http://localhost:3000 (the health check is at `/api/health`).

Before your first e2e run, install the test browser with `npx playwright install chromium`. To start over with an empty database, run `docker compose down -v`.

## Migrations

Add a new file `db/migrations/NNN_name.sql`, and never edit one that has already been applied. Each file runs in its own transaction, and applied files are recorded in `schema_migrations`.

Migrations **expand and contract**. `deploy.sh` applies a release's migrations while the previous release is still serving, and a rollback runs an older image on the current schema, so a migration only adds what its release needs. Taking something away (dropping or renaming a column or table, changing a column's type, making a column NOT NULL) waits for a later release, once no deployed image uses it, and says so in a comment: `-- contract: events.notes, unread since v1.2.0`. `npm run check:migrations` (in CI) refuses a migration from `015` on that takes something away without one. Waiting now: `events.notes`, `users.password_hash` and `password_changed_at` (with the `accounts_sync_password` trigger), `password_resets`, `user_shows.rating`.

## Design system

The apps and the pages around them (home logged in, `/account`, `/privacy`, the login pages, the 404 and error pages), and the website (home logged out, `/about`, `/privacy` logged out; see [Home and the website](#home-and-the-website)), take their colors from the user's theme, Light or Dark ([components/common/themes.module.css](app/components/common/themes.module.css), each with its own accent; [lib/themes.ts](app/lib/themes.ts) shows Light for a theme id it doesn't know), and every size from one set of scales on the app shell ([components/common/AppShell.module.css](app/components/common/AppShell.module.css)): corners (`--radius-xs` to `--radius-xl`), text (`--text-2xs` to `--text-3xl`, three weights), spacing (4 px steps), shadows and motion. A rounded box inside another, close to its edge, has the outer radius less the room between them. The common parts are components, [components/common/ui.tsx](app/components/common/ui.tsx) (`Button` and its variants `primary`, `remove`, `danger` and `quiet`, `Alert` with Retry or ×, `Notice`, `Confirm`, `SrOnly`), on [components/common/ui.module.css](app/components/common/ui.module.css) (headings, cards, fields); the variants are on `.button` (two classes), so they win over an app's own rules for the buttons in its views, and the apps keep no copies of them. Undo is one component too ([components/common/Undo.tsx](app/components/common/Undo.tsx)): a message at the bottom of the screen (over the tab bar on a phone) with Undo for 5 seconds, paused while the pointer or focus is on it, for what is deleted or left; only what can't be undone asks first. Icons are the one line set in [components/common/icons.tsx](app/components/common/icons.tsx), with no text glyphs standing in for them. Type: kerning on, headings on tight leading (`--leading-tight`, `--leading-snug`) and tracked a little tighter, small capitals a little looser (`--tracking-wide`), prose at most 65 characters a line (`--measure`), no widows (`text-wrap: pretty`), and numbers that line up or change in place in tabular figures (`time`, `data`, counts). While a dialog is open (and the page can't scroll), the page keeps its scrollbar's room if it had one (`scrollbar-gutter`, set by `Dialog.tsx`), so nothing behind shifts sideways; colors derived from the theme's are mixed in OKLCH. Motion follows one system ([docs/decisions/0013](docs/decisions/0013-motion-system.md)): its tokens are on the app shell, the same numbers in [lib/motion.ts](app/lib/motion.ts), and its parts in [components/common/motion.tsx](app/components/common/motion.tsx). Entrances ease out, moves ease in and out, exits are 20% shorter, nothing overshoots but the Shows guide's last step; dropdowns take 180 ms, dialogs 220 ms. A pressed button scales to 0.97; popups grow from 0.95 out of what opened them and go back into it; a segmented control's thumb and the tab bar's underline are one object sliding (and stretching 12%) between options; list rows come in 30 ms apart; changing icons crossfade with a blur; a success pulses; something dragged follows the finger and rubber-bands past its bounds. All of it stops with reduced motion. There is one font, the system's; the only monospace text is an invite code, shown in two groups of four. On the front page (home, logged out), in a browser window and scaled up with it (`zoom`), and in its login prompt, each app has a picture of itself ([components/site/AppPreview.tsx](app/components/site/AppPreview.tsx)), drawn in the page's theme. Avatars without a picture show two initials from the name (`DM`; the username's first letter without a name, `lib/names.ts`). Password fields have Show/Hide. Log in and Sign up follow one rule wherever they are side by side: Log in first and plain, Sign up after it and filled with the accent.

## Shared spaces

`/shared` is a calendar and task lists for a couple (up to 10 people can join). It offers creating or joining a space until the user has one ("Your shared calendar"), then opens Calendar. A space has no name (`012` dropped `spaces.name`): it is its members, calendar and task lists, and creating one is a button; a space of one has Invite your partner over its calendar (Share invite link, or Not now, remembered on the device) until someone joins. Its tabs are Calendar, Tasks and Settings, each at its own URL (`/shared`, `/shared/tasks`, `/shared/settings`). Settings has the members (each with their profile picture, or initial, in a ring of their color, then their name and @username: `Diogo Mota (@diogofrmota)`), Invite someone, Calendar in your phone (see [Shared calendar](#shared-calendar)), Recent activity (what the members did lately: joined, added or changed an event, made a list, added or ticked off a task; 60 days; the latest 5 lines with Show more, and a run of one thing by one person within the hour as one line, `Diogo added 9 tasks to Home and Groceries`), and Leave this space, which is done with Undo, or, as the last member, asks first (Leave and delete: the space and its data go). Each space supports up to 10 members, with distinct named colors; ownership passes by join time.

Any member invites: **Share invite link** makes a single-use link, `/join/<code>`, valid 24 hours, and opens the phone's share sheet (or copies it where there is none); the link and its 8-character code are shown, with Copy link and when it expires (`14 Nov 2026, 15:30`: Lisbon time, the 24-hour clock, the day first). The link's page ([app/join/[code]](app/app/join/[code]/page.tsx)) says who sent it ("Ana invited you to Shared"); logged out, it has Log in and Sign up, which come back to it; logged in, Join (opening it never joins, so a link preview can't); a used, expired or unknown code says so, and someone already in a space is told to leave theirs first. The code also works typed in Join space.

The authenticated JSON API is `/api/shared/spaces`, one route file per endpoint, each on `apiRoute` ([lib/http.ts](app/lib/http.ts): the session, changes only from this site, JSON bodies checked by the zod schemas of [lib/schemas.ts](app/lib/schemas.ts)): `GET` reads your space (`{id, ownerId, members}`, each member `{id, username, avatarUrl, name, color, role}`), `POST {}` creates one, and `POST /join {code}` joins. `GET /:id` reads a space, `POST /:id/invites {}` makes a code (`{code, expiresAt}`), and `POST /:id/leave {}` leaves. `GET /api/shared/activity` is the space's recent activity. Responses contain `data` or an `error` message. Reads and mutations check current database membership, inside the same transaction; another space's id answers 404. Requests lock the rows they depend on, the user's then the space's ([lib/spaces.ts](app/lib/spaces.ts)): the calendar's and tasks' share them (`FOR SHARE`), so members work at the same time and other spaces are never in the way; joining, leaving and creating take them alone (`FOR UPDATE`), so two people can't take the last place or the same color, and a member can't leave halfway through a request that assigns them something. Join attempts are limited to 20 per 15 minutes per user. Migration `004_space_membership.sql` records join times and enforces unique member colors within a space; `017` records who made an invite.

## Shared calendar

Calendar has Month and Agenda views. The agenda is the default on a phone, the month on a wide screen. One compact toolbar, all of it together in the middle, has the month and year with ‹ and › on either side of it (`Nov 2026` on a phone), then Month | Agenda, both always there with the one showing raised in the accent, and Add event; ‹ and › move by a month, to its first day, or to today in the current month. There is no Today button, day/week view or color legend. The month uses the full page width; the agenda's days are a centered column with the page's margins, under the same full-width toolbar, which stays where it is whichever view is showing (the page's scrollbar keeps its room in Shared, so the toolbar doesn't move by half of it either). On a wide screen a month's events are one-line bars, in lanes week by week (`layoutWeek`, [lib/calendar.ts](app/lib/calendar.ts)): an event of several days is one bar across them, a timed one starts with its time (`09:00 Dentist`), and a day shows two lanes, followed by "+N more", which opens the agenda from that date. On a phone a day of the month is its number and a short colored bar for each event (three, then `+1`), and a tap on a day picks it, ringed in the accent: its events are listed under the month, with Add event for that day (the month's own day, today or its first, to start with). An event for two people or more is half one person's color and half the other's. Swiping the month moves to the previous or next month. The agenda lists every event from today on (or from the first of the month moved to), by day, 20 at a time (`GET /api/shared/events?from=&limit=`, [lib/events.ts](app/lib/events.ts) `listUpcomingEvents`); Show more adds the next 20 under them, and goes once there are no more. The page scrolls down through them. Each event shows its title and the assigned members' pictures (or initials), and an event of several days which of them it is (`day 1 of 2`); its times and full assignment are in its dialog and accessible label. Existing group events remain readable. New events select individual members, including everyone by selecting each person. Event dialogs are centered popups with margins at every screen size, as tall as what is in them, and scroll internally when needed. Escape and browser Back close them, and an open event is in the URL.

Times are entered and displayed in `Europe/Lisbon`, regardless of the device time zone, on the 24-hour clock, and stored in PostgreSQL `timestamptz` as UTC instants. The event form, Create a new event, has the Event title, the dates and times, and Who?: each member a chip, their picture (or initials) and first name, ringed in their color when chosen, by their full name for screen readers, **any number of them**, including everyone by selecting each member ([components/shared/MemberPicker.tsx](app/components/shared/MemberPicker.tsx)); the one adding it is chosen to start with. Events have no notes. Dates and times are typed, not the browser's fields, which follow the device's language and can show AM and PM: a date shows `dd/mm/yyyy` while empty and its blanks, `__/__/____`, once focused, which fill in as it's typed (number keys on a phone), and a time `__:__`; focused, the field is all selected, so typing starts it over. A date that isn't real (31/02) or a time past 23:59 stops the form, saying what to type. A new event starts on the day tapped (or the one shown). On a wide screen, where the six weeks don't have room for two lanes a day, the month scrolls as a whole. The form's button is Save. On one day, a new start time moves the end time with it, keeping the event's length. Events can span dates. A click on a day of a wide month adds an event that day; on a phone, Add event under the month does, for the day picked. All-day events (`events.all_day`, from `011`) run from the start of their first day to the start of the day after their last, show as All day in the agenda, and export as whole days. Nonexistent spring-forward times are rejected; repeated autumn times offer first/second occurrence choices. Delete event closes it with Undo. Only the days shown are loaded, and each period loaded stays (in memory, and in the browser for offline use) while the next one loads.

Exports: per event, from the event's dialog, Add to my calendar, a button that opens Google Calendar and Apple or Outlook (.ics) (a download), each saying who it's for; and the whole calendar as a **subscription**, from Settings, Calendar in your phone: one secret link per user, `/api/calendar/<token>` ([lib/calendar-feeds.ts](app/lib/calendar-feeds.ts)), the space's events from 3 months ago on, which Google, Apple or Outlook Calendar check every few hours (Add to my calendar opens it as `webcal:`; Copy link for Google's From URL), with that app's own reminders. The link is hidden at first: its field blurred, its secret as dots, with Show in it, which takes the blur and itself away and selects the link. Whoever has the link reads the calendar; Make a new link (which asks first) stops the old one. The files use UTC timestamps, escaped text, CRLF and UTF-8 line folding per [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545).

`/api/shared/events`: `GET` lists your space's events (`?from=&to=`, UTC instants at most 400 days apart: those overlapping the range), `POST` creates one; `GET /:id`, `PATCH /:id` and `DELETE /:id` read, replace and delete an event. Create/replace accepts `{title, startsAt, endsAt, allDay, isGroup, assigneeIds}`; timestamps must be ISO UTC strings ending in `Z`, end must follow start, an all-day event runs from midnight to midnight, and a group event has no `assigneeIds` while any other has one or more current members. All space members can manage events. `GET /:id/export` downloads an event as `.ics`; `GET /api/shared/calendar-feed` answers with your subscription link (`{url, webcal}`, made the first time), and `POST` makes a new one. Every operation checks current membership inside the same transaction as the read/write. A departing member is taken off their events; an event left for nobody is labeled Former member until reassigned; they cannot access their previous space. `events.notes` stays, unread, until a contract migration.

## Shared tasks

Tasks holds any number of lists per space, shown as chips above the open list (from 64rem, a column beside it); the last list opened is remembered on the device. The open list's name has how many tasks are left to do after it, `Groceries (3)`, and new tasks are written in Write a task under it. Edit (or New list) creates, renames, reorders and deletes lists; deleting a list shows it as deleted in its row, with Undo, for 5 seconds, and then deletes it with its tasks (closing Edit deletes it at once). A task has a title, an optional due date, notes and **Repeat** (Every day, week, month or year), and zero or more assigned members, shown as small profile pictures. A task's row is one line that wraps: the title, then the members' pictures, the due date (Due today in the accent, Overdue in red), how often it repeats and the notes, each going under where it doesn't fit. Its dialog (a tap on the task) has the title, Who?, Due date (with Today, Tomorrow and Next week a tap away), Repeat?, Notes and, with more than one list, List (another one moves the task to its end), followed by Save and Delete. Who? uses the same individual checkboxes as events, with no All shortcut; its × closes it without saving. A task ticked off stays where it is for a moment, ticked and crossed out (it no longer counts as one to do), then fades and slides away into a collapsed Done section, 650 ms in all (`tickedMs` in [useTasks.ts](app/components/shared/useTasks.ts)); a **repeating** one comes back instead, unticked, with its next due date: a period after the last, skipping the ones already past (bins due on Monday and done on Tuesday are due next Monday; a month from the 31st is the end of a shorter month; `nextDue` in [lib/task-types.ts](app/lib/task-types.ts)). The change is only sent then, so unticking it in that moment leaves it as it was; leaving the Tasks view or the page sends it at once. Unticking a task in Done puts it back at the end of the list. Due dates are plain calendar dates, compared with today in `Europe/Lisbon`, typed in the task's dialog as `dd/mm/yyyy` (the event form's date field, [components/shared/MaskedField.tsx](app/components/shared/MaskedField.tsx); not the browser's, which can be `mm/dd/yyyy`), and cleared with Clear. New tasks are entered immediately below the list title, before all existing tasks. Task and list dialogs stay within the viewport with visible margins on phones.

Drag a task (or, in Edit lists, a list) by its handle to reorder it: with a mouse, a finger (the rest of the row still scrolls the page), or the keyboard (Space or Enter to pick it up, the arrow keys, Space or Enter to drop it, Escape to cancel; each step is announced to screen readers). Delete a task with its bin button where there is a mouse, by swiping it left on a touch screen, or from its dialog. Undo is offered for 5 seconds (paused while the pointer or focus is on it), and the delete is only sent once that runs out, or when you leave the Tasks view or the page.

Changes show at once and are sent one at a time, in the order they were made (TanStack Query, [components/shared/shared-data.ts](app/components/shared/shared-data.ts): each change is plain data, applied on screen on top of what the server last sent). If the server refuses one, it is undone on screen with a message saying why; when the reason is that someone else changed the list meanwhile, Tasks reloads. Without a connection, the changes show at once, a note says they wait, and they go out in order once it's back, after a reload too. While Tasks is open it loads again every 5 seconds (and when the browser tab comes back into view), so what the other member ticks off in the shop shows up.

`/api/shared/tasks`: `GET` returns every list of your space with its tasks, both in order. `POST /lists {id?, name}` adds a list at the end, `PATCH /lists/:id {name}` renames it, `DELETE /lists/:id` deletes it with its tasks, and `POST /lists/:id/move {beforeId}` moves it before another list (`null`: to the end). `POST /lists/:id/tasks {id?, title, notes?, dueDate?, assigneeIds?, isComplete?, repeat?}` adds a task at the end of a list; `PATCH /:id` changes any of those fields of a task (ticking off a repeating one moves its due date on instead), `DELETE /:id` deletes it, and `POST /:id/move {beforeId}` moves it before another task of the same list, or `{listId}` to the end of another list of the space. Ids are UUIDs, and clients may choose the ids of what they create (one already in use is a 409), so later changes can refer to a list or task before its response arrives. List names are 1–80 characters, titles 1–200, notes up to 10,000; `dueDate` is `YYYY-MM-DD` or `null`; `assigneeIds` is an array of up to ten current members (empty for no assignment); legacy `assigneeId` is supported for cached clients and rollback; `repeat` is `daily`, `weekly`, `monthly`, `yearly` or `null` (`018`). Every operation checks current membership inside the same transaction as the read/write, and another space's lists and tasks answer 404. A member who leaves loses their assignments.

## Shows: TMDB and Discover

Discover (`/shows/discover`) has a TV Shows | Movies switch, remembered on the device, over sections, each one row of up to 20 cards that scrolls sideways: a swipe on a touch screen (the cards snap into place, and the next one peeks in), and with a mouse a drag, a trackpad's sideways scroll or the ‹ › buttons that show over the row's ends while the pointer is on it (only towards more); the end with more to see fades out, and the keyboard goes from card to card. A section loads once it comes near the screen (a screen's height away), so opening Discover on a phone loads what is seen first. In this order: Recommended by Friends (what friends recommended to you, each card saying who from, `From Ana`, until it's in your library; only when there is something; shown, they are seen, and home's badge stops counting them), Added by Friends (see below), For You (only with titles of that type in the library: TMDB's recommendations for up to 5 of them, favourites, then completed and watching ones first, merged so a title recommended for several or near the top comes first, without the titles already in the library or in Trending and Popular), Trending This Week, Popular, for movies Coming Soon (upcoming), Top Rated (TMDB's discover sorted by rating, from titles with at least 500 votes for TV and 2,000 for movies), and three genres (TV: Comedy, Crime, Sci-Fi & Fantasy; movies: Action, Comedy, Science Fiction; each the most popular of the genre). Added by Friends is titles in the libraries of accepted friends, any status, the ones most friends have first; see [Shows: Profile and friends](#shows-profile-and-friends)). Every section from TMDB leaves out titles with fewer than 50 votes (TV) or 100 (movies), so a handful of 10s can't put something hardly anyone has seen at the top (Coming Soon's titles aren't out yet, so they need none). A title is shown only once, in the first section it would be in, in the order Trending, Popular, Coming Soon, then the genres; Top Rated and Added by Friends repeat what they like. The next pages of TMDB's list (up to 3) fill the places of the titles left out, so each section has 20. For You loads again after the library changes. Cards show the poster, title, year and TMDB's average rating, and a title in the library that is Watching or Completed says so at the poster's top left (as everywhere a poster is). The search field at the top of Discover (and Search on an empty Library), centered over the TV Shows | Movies switch, opens the search panel (the whole screen on a phone): it searches TV shows and movies together, 300 ms after typing stops, the exact title first, then titles that start with what was typed, and in each the ones with a poster and enough votes (50 for TV, 100 for movies) first. A card opens the detail panel (see [Shows: Library](#shows-library)). A + at the bottom right of every Discover and search poster ([components/shows/AddToLibrary.tsx](app/components/shows/AddToLibrary.tsx)) opens Planned, Watching and Completed over the poster, each its icon and name in the middle of a pill; Watching a TV show then asks, over the poster, the last episode watched (Season and Episode, the first one to start with, and Save; leaving it with Escape or a tap elsewhere keeps it Not started). Once the title is in the library the + is a tick, which opens its quick actions. Loading sections show grey skeleton posters; a failure shows a message with Retry. At the bottom of Discover and of a title's panel, TMDB's logo (linking to TMDB) and "This product uses the TMDB API but is not endorsed or certified by TMDB." ([components/shows/TmdbAttribution.tsx](app/components/shows/TmdbAttribution.tsx)), as [their terms](https://www.themoviedb.org/api-terms-of-use) ask.

[app/lib/tmdb.ts](app/lib/tmdb.ts) is server-only: it sends `TMDB_READ_TOKEN` (the v4 API Read Access Token) as a Bearer token, gives up after 8 s, and checks every field of TMDB's answers. The browser only calls `/api/shows` and loads posters from `image.tmdb.org`, in TMDB's sizes from `w92` to `w780` (the closest for each width of next/image's srcset). TMDB's list pages and the sections made from them stay in memory for 10 minutes, searches for 5, a title's recommendations for 6 hours. Opening a title or adding it to a library upserts it into `shows`: title, year, poster path (in `poster_url`, e.g. `/abc.jpg`), overview, genres (up to 5 of TMDB's names, `020`), movie runtime, typical episode runtime (the latest episode's when TMDB has none), episode count of each regular season (no specials) and TMDB's rating (`vote_average`, added by `005_show_rating.sql`). A copy older than 7 days, or without genres, is fetched again the next time it is opened or added, and kept as it is if TMDB can't be reached. TMDB allows caching for at most 6 months: titles nobody opens again would keep their last copy, so loading the library also refreshes its titles older than 7 days (see [Shows: Library](#shows-library)).

The authenticated JSON API: `GET /api/shows/discover/{tv|movie}/{section}` returns a section (`recommended`, `for-you`, `trending`, `popular`, `top-rated`, `comedy`, `sci-fi`, `friends`, and `crime` for TV, `upcoming` and `action` for movies), `GET /api/shows/discover/search?q=` the TV shows and movies matching `q` (1–100 characters; people and collections are left out), `GET /api/shows/titles/{tv|movie}/{tmdbId}` a title's details with your library entry (or `null`) and `friends` (your friends who have it, `{id, username, avatarUrl, name, status}`), `GET /api/shows/titles/{tv|movie}/{tmdbId}/similar` More like this, `POST /api/shows/library {type, tmdbId, status}` adds a title as `watching`, `planned` or `completed` (201, or 409 if it is already there), and `POST /api/shows/recommendations {friendId, type, tmdbId}` recommends a title to a friend (201; 404 for someone who isn't); the rest of the library API is under [Shows: Library](#shows-library). Responses contain `data` or an `error` message; when TMDB fails they answer 502 (404 for a title TMDB doesn't have). Each user can make 240 requests a minute.

In the e2e tests no request reaches TMDB: with test hooks on, `lib/tmdb.ts` hands its requests to a fake TMDB in the same process ([app/lib/tmdb-mock.ts](app/lib/tmdb-mock.ts); `/api/test/tmdb` lists what it answered), and `e2e/fixtures.ts` answers the browser's poster requests with a placeholder. The fake's ids start above 2,100,000,000, and the teardown deletes the titles it put in `shows`.

## Shows: Library

Library (`/shows`, the first tab; it was the Watchlist, and Home before) is the user's library: a TV Shows | Movies switch, remembered on the device, over three sections, Watching, Planned and Completed, each listing the titles changed most recently first (whole rows until Show all: three rows when the grid has four columns or fewer, as on a phone, two when wider). The switch is on the left, and past 6 titles of a type a search (by title) and a sort (Recently updated, A–Z) are beside it. A card shows the poster (with a heart for a favourite, and Watching or Completed at its top left where statuses are mixed, as in Favourites, Discover and a friend's profile, not in Library's own sections, whose heading says it; and, on every poster of a title Watching or Completed, a friend's too, a line along its bottom edge from the left: as long as the share of a TV show's episodes watched, none at first and half way at half of them, in the Watching badge's blue, then all the way across in the Completed badge's green once completed), the title and year, and the progress of a TV show being watched (`S2 E5`, or `Next: S1 E1` before the first), with a button under it that marks its next episode watched in one tap (`✓ S2 E6`): it turns green at once, its tick drawing itself and a ring of green spreading from it, for the episode just watched, and after 900 ms the next episode comes in from below (`NextEpisodeButton`, [LibraryGrid.tsx](app/components/shows/LibraryGrid.tsx)). In a title's panel, a show being watched has its progress first, above the synopsis. Users don't rate titles: the only rating is TMDB's. A library that is empty when the app opens (a new account's) shows a guide instead ([components/shows/Onboarding.tsx](app/components/shows/Onboarding.tsx)), in three numbered steps: TV shows, then movies (this week's trending and the popular ones, or a search of that kind; a tap on a poster opens Planned, Watching and Completed over it, Watching a TV show then asks the last episode watched, and the title's status again takes it out), then Watch together (Add a friend); Finish shows what was added, by status, with Go to my library. Skip ends it at any step, and so does coming back to Library from another view with titles in the library. Without it, an empty library shows "Start by discovering shows!" with Go to Discover, Search and Set up step by step (the guide again); an empty section says so, with a link to Discover. Adding a title in Discover or search shows it in Library at once.

A tap or click on a card opens the detail panel ([components/shows/TitleDialog.tsx](app/components/shows/TitleDialog.tsx); its URL has it, `?p=title:tv:1396`), laid out as the title's page, over a blurred copy of the poster: on a wide screen, the poster with the title, type, year, TMDB rating, its genres (`Drama · Mystery`) and length (seasons and episodes, or a movie's runtime) under it, in a column that stays in view, and beside it Synopsis, the overview (cut to four lines, with More and Less, when it is longer), then **Friends** (your friends who have it, each with their picture, name and how far they are: Watching, Watched it, or Wants to watch it for a favourite they planned), then what can be done with it, the seasons, **Recommend to a friend** (your friends, Send each: it shows in their Discover until they add it), **More like this** (TMDB's recommendations for people who liked it, posters in a row with a visible scrollbar), Remove from library without a divider, and TMDB's notice; on a phone the poster is small, beside the title, with the rest under both. A title not in the library has Add to Library: Planned, Watching and Completed as three tiles with their icons. One in the library has its status (Planned | Watching | Completed, with their icons, one over the other on a wide screen) and Favourite under the poster and the facts (that it is in the library is only said to screen readers), and beside them, in a panel, the progress of a TV show being watched (the last episode watched, a bar and "4 of 18 episodes watched", Next episode, which moves on to the next season after a season's last episode, then a season and an episode picker, [components/shows/EpisodePicker.tsx](app/components/shows/EpisodePicker.tsx)). Its seasons show which are watched (a tick, on the faded green of a completed title) and how far into the current one (`4 of 10 episodes`). Remove from library is at once, then says so with Undo, which adds it back as it was (status, progress, favourite), and the Add to Library tiles. Setting the progress to the last episode offers Mark as completed (or Not yet). Progress is the last episode watched, and is kept when the status changes. Quick actions, for the status (and the season and episode of a TV show being watched), open from the ⋯ button on a card where there is a mouse (it shows on hover or focus), from a right click, or from a long press (half a second) on a touch screen: a small menu beside the card on desktop, a sheet from the bottom on a phone. Back or Escape closes either.

Changes show at once and are sent one at a time, in the order they were made (TanStack Query; [components/shows/library.tsx](app/components/shows/library.tsx)); if the server refuses one, it is undone with a message (and the library reloads after a 404 or 409, e.g. a title removed in another tab). The library loads with the app and again whenever the page becomes visible, and is kept in the browser for offline use; changes made offline wait and go out once the connection is back.

`GET /api/shows/library` returns the library, latest change first: each title's card fields and lengths (`runtime`, `episodeRuntime`, `episodesPerSeason`, for the stats) with its `library` entry (`status`, `currentSeason`, `currentEpisode`, `isFavourite`). `PATCH /api/shows/library/{tv|movie}/{tmdbId} {status?, isFavourite?, currentSeason?, currentEpisode?}` changes your entry for a title and returns it: the progress (TV only) is both fields together, an episode the show has according to its cached seasons, or both `null`. Anything else in the body is ignored, `rating` too (users used to rate titles; `user_shows.rating` keeps the old ratings, unread, so an older image still works). `DELETE` on the same path removes it from your library. Both answer 404 for a title that isn't in your library, so nobody can change anyone else's. `006_library_updated_at.sql` adds `user_shows.updated_at`, set by every add and change, for the order. Loading the library answers with the cached copies and then, after the response, fetches the titles older than 7 days from TMDB again, one at a time, stopping at the first failure. Adding a title, a new status and a new favourite go in your friends' activity feed.

## Shows: Profile and friends

Profile (`/shows/profile`) is one column in the middle of the page, every block as wide as it. From the top, in the middle: your profile picture (or initial), your name under it and your @username under that (the @username alone without a name), and nothing else; the friend requests you received, with Accept and Decline (only when there are any); Stats; Favourites (the titles marked Favourite, TV shows and movies together, latest change first, whole rows until Show all, with Library's quick actions); **Friends' activity** (what your friends started watching, planned, finished, made a favourite or recommended, newest first, 60 days; a title opens its panel; [components/common/ActivityFeed.tsx](app/components/common/ActivityFeed.tsx)); and Friends: a field, Add a friend (Their username), which from 2 characters lists up to 6 people whose username, name or a word of their name starts with what's typed (`mota` finds `Diogo Mota`; in any case and without accents; after an `@`, usernames only), each as their picture, name and @username, `Diogo Mota (@diogofrmota)`, with how you're connected (Friends, Request sent, Sent you a request; arrows and Enter or a tap pick one, which puts their username in the field, and Escape closes the list), and says whether an account has exactly that username. Send request asks it, or with a name typed, the one person found (for several, it says to choose someone from the list). Then your friends, each a row with their picture, name and @username and Check profile, which the whole row opens, and a bin to remove them, at once with Undo (on a phone, the name and @username on one line, and Check profile and the bin under it); and the requests you sent (with Cancel). Each answer, or the reason it was refused, shows in the section it was made in; when the button pressed goes away with its row, focus moves to that message. Friend requests and answers apply to both people at once; the other person sees them the next time their Profile loads, which it does whenever it is shown and when the page becomes visible again.

Stats: TV shows completed and movies completed on the first row, then hours watched below them. Hours watched is each TV show's episodes watched times its episode runtime, plus the runtime of each completed movie, rounded to one decimal. A show being watched counts up to its current episode included (S2 E5 after a first season of 10 is 15 episodes), a completed show all of its episodes, a planned one none (even with progress from before); a movie counts once completed. Runtimes are TMDB's, from the `shows` cache; a title without one counts 0 minutes. Your own stats follow every change at once: the browser works them out from the library with `libraryStats` ([app/lib/show-types.ts](app/lib/show-types.ts)), the same function the server uses for a friend's.

A friend's row opens their profile (the whole screen on a phone, `?p=friend:<id>`; Back or Escape closes it), read-only: their stats, Watching, Completed, Favourites, and **You both want to watch** (the titles you've both planned). Planned titles that aren't favourites are left out, of the API answer too. A card opens the title's detail panel on top, about your own library, so you can add it. Added by Friends in Discover loads again, when it is next shown, after Profile sees your friends change.

Friendships use the `friendships` table from `001_initial.sql`: one row per pair of users, `user_id` sent the request. It is pending until the other person accepts; declining, cancelling and removing delete the row, so either of them can ask again later. Asking someone who has already asked you accepts their request (in one statement, so two people asking each other at once become friends).

The authenticated JSON API, under the same rules as the rest of `/api/shows` (changes only from this site, JSON bodies, 240 requests a minute per user): `GET /api/shows/friends` returns `{friends, incoming, outgoing}`, each a list of `{id, username, avatarUrl, name}` by username (`avatarUrl` is their profile picture, or `null`, and `name` `null` until they set one; everywhere a person is shown, so are they). `GET /api/shows/friends/search?q=` returns `{matches, exact, self}`: up to 6 people as above with their `relation` (`none`, `friend`, `incoming`, `outgoing`), whose username, name or a word of their name starts with `q` (2–50 characters, spaces tidied; names compared in lowercase and without accents, with `013`'s `unaccent`; after an `@`, only usernames, so only a-z, 0-9 and _; anything else answers no matches), the exact username first, then the other usernames, then names, never yourself; whether another account has exactly `q` as its username, and whether it is yours; 60 searches a minute per user. Usernames are served by `010`'s prefix index on `users.username`; names have no index (there are a handful of accounts). `POST /api/shows/friends {username}` sends a request, or accepts theirs (201); it answers 400 for an empty or impossible username or your own, 404 when no account has it, 409 when you are friends already or have already asked, and 429 after 20 requests in 15 minutes, because each answer tells whether a username exists. `POST /api/shows/friends/{userId}/accept` and `/decline` answer a request they sent you, `/cancel` withdraws one you sent (each with `{}`), and `DELETE /api/shows/friends/{userId}` removes a friend for both of you; these answer with the new `{friends, incoming, outgoing}`, or 404 when there is no such request or friendship. `GET /api/shows/friends/{userId}` returns a friend's profile: `{id, username, avatarUrl, name, stats, items, bothPlanned}`, where `stats` is `{tvCompleted, moviesCompleted, episodesWatched, minutesWatched}`, `items` their watching and completed titles and favourites, latest change first, each with its `episodesPerSeason` (for the progress line) and `library: {status, currentSeason, currentEpisode, isFavourite}` (no entry ids), and `bothPlanned` the titles you've both planned. Anyone who isn't an accepted friend (a pending request, a stranger, yourself, an id nobody has) gets 404, "Only friends can see each other's libraries." `GET /api/shows/activity` is your friends' recent activity.

## Recipes

`/recipes` ([components/recipes/](app/components/recipes/), [docs/decisions/0017](docs/decisions/0017-recipes.md)) keeps the recipes a user wants to cook again, with a shopping list. They are the user's own: nobody else sees them. Its tabs are Recipes, Favourites and Shopping, each at its own URL (`/recipes`, `/recipes/favourites`, `/recipes/shopping`); a recipe's page is a panel (`?p=recipe:<id>`), and its form one over it (`&p=edit:<id>`, or `?p=new` for a new one).

**Recipes** has a search (every word of it in the title, tags, ingredients or notes, in any case and without accents: `creme` finds Crème brûlée), a sort (Newest, A–Z) and New recipe; then every tag of the recipes as chips (All, then each tag as it was first written, A to Z) to pick one; how many there are (`3 recipes`, `2 of 3 recipes` while searching or with a tag); and the recipes as cards, two across on a phone and more wider: the cover photo (or a book on the accent's tint), the title and the tags, and a heart on the photo's corner that makes it a favourite in one tap. A card opens its page. With none, "Your recipes, in one place" says what the app is for, with Add your first recipe. **Favourites** is the same with the favourites only (none: "No favourites yet", with Go to your recipes).

A **recipe's page** ([RecipeDialog](app/components/recipes/RecipeDialog.tsx)) has its photos, its title, Serves N and From `<site>` (its source link, in a new tab), its tags, Favourite and Edit; the ingredients beside the method on a wide screen (over it on a phone), the method's steps numbered; its notes; and Delete recipe, which closes it with Undo. **Servings**, with − and + (1 to 100), scale the ingredients from the servings the recipe was written for, and Reset to N goes back: each line's first amount, or range (`2-3 cloves`), is multiplied ([lib/recipe-types.ts](app/lib/recipe-types.ts), `scaleIngredient`) and written as it was: whole numbers and fractions (`1/2`, `1 1/2`, `½`) as whole numbers or fractions where one is close (`1½ cups`), else a short decimal; decimals as decimals, with their comma (`0,75 l` doubled is `1,5 l`); from 10 up, whole numbers (`67 g`). Not a percentage (`5% fat`) nor a 0 (`Type 00 flour, 500 g` scales the 500); a line without an amount (`Salt, to taste`) and a heading (a line ending in a colon, `For the sauce:`, shown as a small heading) stay as they are. **Add to shopping list** turns the ingredients into checkboxes, all ticked but the headings and scaled to the servings chosen, to untick what's in the cupboard; Add N items to the list adds the rest to the end of the list and says so, with Open it.

**Photos**: up to 10 a recipe, the first its cover. With none, the top of its page is a place to drop one or choose it (the file picker; on a phone, the photos or the camera); with some, the one picked is large (the cover to start with; a link to it full size), with Make cover and Remove photo over it, and the thumbnails under it, then + to add more (several at once too). Photos need the connection and the recipe saved on the server (a recipe made offline says so until then): they are sent at once, not queued. Removing one waits for its Undo, which is in the recipe's page (it's modal, so the page's message behind it can't be reached). The server makes each one smaller ([lib/recipe-photos.ts](app/lib/recipe-photos.ts)), as it does profile pictures: upright as its EXIF says, at most 1,600 px a side, and a 640x480 copy cut around what stands out for its card, both WebP without metadata; files up to 20 MB and 70 megapixels, 30 uploads per 15 minutes per user. Each is two files, `RECIPE_PHOTO_DIR/<photo id>.webp` and `<photo id>-thumb.webp` (`/app/data/recipe-photos` in the image, on the `appdata` volume, archived by [infra/backup.sh](infra/backup.sh) as `recipe-photos_*.tar.gz`; `app/data/recipe-photos` with `npm run dev`, which git ignores). nginx lets 21 MB through to their upload.

**The form** ([RecipeForm](app/components/recipes/RecipeForm.tsx)), New recipe or Edit recipe: Title, Serves (4 to start with), Ingredients and Method (one a line; the bullets and numbers of a list pasted from a website are left out), Tags (each a chip with × to take it off; Enter or a comma adds the one typed, and one typed but not added counts on Save; the user's other tags are a tap away), Source link (read generously: `bbcgoodfood.com/…` is `https://bbcgoodfood.com/…`; anything but an http(s) link is refused) and Notes. Save checks them as the API does, marks each field to fix with why, and focuses the first; saved, it closes, and a new recipe's page opens, for its photos. Its × closes it without saving.

**Shopping** has To buy (and how many), Add an item, then the lines in the order they were added, each with its box to tick off, the recipe it came from (a pill that opens it) and a bin; and Ticked off under it, crossed out, with Clear ticked. A line deleted and Clear ticked wait for their Undo. With nothing to buy: "Nothing to buy yet. Add what you need here, or a recipe's ingredients from its page."

Changes show at once and are sent one at a time, in the order they were made (TanStack Query, [components/recipes/recipes-data.tsx](app/components/recipes/recipes-data.tsx): each change is plain data, applied on screen on top of what the server last sent; one queue for the recipes and the list, so a recipe made offline is saved before its ingredients go on the list). If the server refuses one, it is undone on screen with a message saying why; after a 404 or 409, both load again. Offline, they wait, and go out once the connection is back, after a reload too.

`/api/recipes` ([lib/recipes.ts](app/lib/recipes.ts), on `apiRoute`, 240 requests a minute per user): `GET` returns your recipes, newest first, each `{id, title, servings, ingredients, steps, notes, sourceUrl, tags, isFavourite, photos: [{id, width, height}], createdAt, updatedAt}`; `POST {id?, title, servings?, ingredients?, steps?, notes?, sourceUrl?, tags?, isFavourite?}` adds one (201); `GET`, `PATCH` (any of those fields) and `DELETE /:id` read, change and delete one (with its photos; its lines on the shopping list stay, from no recipe). `POST /:id/photos` (a multipart form, the file as `photo`) adds a photo (201), `DELETE /photos/:photoId` removes one and `POST /photos/:photoId/cover {}` makes it the cover, each answering with the recipe; `GET /photos/:photoId` (`?size=thumb` for the card's) is the WebP, kept by the browser for good (a photo never changes). `GET /shopping` returns the list, `POST /shopping {items: [{id?, text, recipeId?}]}` adds lines to its end and answers with them, `PATCH /shopping/:id {text?, isChecked?}` changes one, and `POST /shopping/remove {ids}` takes some off. Titles are 1–200 characters, servings 1–100, up to 200 ingredients of 300 characters and 100 steps of 2,000, notes up to 10,000, a source link up to 2,000 (http or https), up to 20 tags of 30 characters (kept without a second one in another case), lines of the list 1–300 characters and up to 500 of them. Ids are UUIDs, and clients may choose the ids of the recipes and lines they create, so later changes can refer to them before the answer comes; sent again with an id already yours, it answers with what is there (a change sent twice), and one someone else has is a 409. Another user's recipe, photo or line answers 404, as one that doesn't exist; a line added from a recipe that isn't yours is from no recipe. `023_recipes.sql` makes `recipes`, `recipe_photos` and `shopping_items`.

## Fitness

`/fitness` ([components/fitness/](app/components/fitness/), [docs/decisions/0018](docs/decisions/0018-fitness.md)) plans workouts and tracks fitness, hydration and body weight. It is the user's own: nobody else sees it. Its tabs are Today, Workouts and Progress, each at its own URL (`/fitness`, `/fitness/workouts`, `/fitness/progress`); its panels are a workout (`?p=workout:<id>`), Start a workout (`start:<date>`), a routine's form (`new-routine`, `routine:<id>`), a run's (`new-run:<date>`, `run:<id>`), Supplements (`supplements`) and Daily goals (`goals`).

**Today** is a day of the log, today to start with: its name (Today, Yesterday, `Mon 16 Nov`) and date between ‹ and ›, which go a day back or on (never past today), and Back to today on another day. Its cards: **Training**, the day's workouts (`Push day`, `3 exercises · 9 of 12 sets · 3,240 kg`) and runs (`5.2 km · 28:30 · 5:29 /km`), each opening its panel, with Start workout (Add workout on another day) and Log a run; **Water**, the day's ml against the goal (`1,250 of 2,000 ml` and a bar, green once the goal is met), with − (250 ml less), + 250 ml and + 500 ml, and Goal 2,000 ml, which opens Daily goals; **Steps**, typed in and saved with Save (`8,500`, `8.500` and `8500` are all read; emptied, Save clears it), against its goal; **Body weight**, typed in kg (`78,4` too), with the change since the last weigh-in (`−0.6 kg since Mon 16 Nov`), or the last one on a day without; and **Supplements**, each a checkbox (`Creatine · 5 g`) with `1 of 2 taken`, and Edit (or Add supplements) opening Supplements: each with its dose and a bin (gone at once, with Undo in the dialog), and Add (Name, and Dose if any), up to 30. Daily goals has the water (250–10,000 ml, 2,000 to start with) and the steps (500–100,000, 10,000).

**Workouts** has the **Routines** as cards (the name, each exercise with its sets × reps, Start and Edit) and New routine (with none, "Plan your workouts" and Create your first routine), then the **History**: every workout and run, newest first, by month, each its weekday over its day's number and what it was, All | Workouts | Runs, 20 at a time with Show more. A routine's form has its Name, its Exercises, each a row (its name, the ones written before suggested; Sets × Reps, 3 × 10 to start with; move up, move down, remove; on a phone the name on a line of its own), Add exercise, and Notes; Save checks them as the API does, marks each field to fix and focuses the first. Delete routine closes it with Undo; the workouts started from it stay.

**A workout** (a wide dialog) has its Name and Day (`dd/mm/yyyy`, typed, as an event's dates are), how far it is (`2 exercises · 1 of 5 sets · 500 kg`, and A personal record when there is one), then each exercise: its name, a bin (it goes at once, its place saying so with Undo, in the workout: the page's message can't be reached behind it), the last time it was done (`Last time, Thu 12 Nov: 60 kg × 8, 7`, from any workout, matched by name in any case and without accents), and its sets as rows: the number, kg, reps (each field saved once it's left, or with Enter; an empty one shows the last time's set) and a tick, which marks it done, green (and, on empty fields, takes the last time's set). A set counts (in the history, its volume and the records) once it's done, with reps. The workout's heaviest set of an exercise, heavier than any before it, has a trophy (the first time an exercise is done has nothing to beat). Add set adds one like the last, Remove set takes the last off; Add an exercise adds one with as many sets as the last time; then Notes, Done (it closes; everything is saved as it's done) and Delete workout (Undo). **Start a workout** lists the routines and Empty workout; the workout opens in its place. From a routine (here, or Start on its card, which is today), its exercises and sets are at its reps and at the weights of the last time each was done, set by set (`workoutFromRoutine`, [lib/fitness-types.ts](app/lib/fitness-types.ts)), so at the gym it is mostly ticking. **A run** has its Day, Distance in km and Time (hours, minutes and seconds, three fields: a phone's number pad has no colon), its pace worked out as it's typed, and Notes; Delete run closes it with Undo.

**Progress** has the **Last 7 days** (workouts with a set done, the distance run, and steps and water a day: the mean of the days logged), **Personal records** (each exercise, the ones done lately first: its heaviest set, more reps first at the same weight and the first time it was set, its date, the estimated one-rep max, Epley's formula from sets of 1 to 12 reps, and how many times it was done, or the most reps for one done without a weight; past six, Show all; then the longest run and the fastest pace of a run of 1 km or more; each opens where it was set), and four charts: **Strength** (an exercise, the one done most often to start with: its heaviest set each day), **Body weight** (30 days, 90 to start with, a year or all of it, with the change over that time), **Steps** and **Water** (the last 14 days, a column a day under the goal's line, with the average of the days logged). The charts ([Charts.tsx](app/components/fitness/Charts.tsx)) are SVG at the width they have: one series each, in the theme's accent (the title says what it is: no legend); a 2px line with a wash under it and its last value at its end, or columns at most 24px wide and 2px apart, rounded at the top; hairline gridlines and ticks on round numbers, in one style an axis (`0, 5K, 10K`; `niceScale`). Hover, a tap, or the arrow keys once a chart is focused, show a day's value; Show as a table has them all. With nothing logged, "Your progress, over time" says what it will show.

Changes show at once and are sent one at a time, in the order they were made (TanStack Query, [fitness-data.tsx](app/components/fitness/fitness-data.tsx), as Recipes does): one answer has everything, each change is plain data applied on screen on top of it, and safe to send twice (a glass of water sends the day's new total, not +250). If the server refuses one, it is undone on screen with a message saying why; after a 404 or 409, it all loads again. Offline, they wait, and go out once the connection is back, after a reload too. Records, the last 7 days and the charts' series are worked out in the browser from what is loaded ([lib/fitness-types.ts](app/lib/fitness-types.ts), unit tested in `test/fitness.test.ts`).

`/api/fitness` ([lib/fitness.ts](app/lib/fitness.ts), on `apiRoute`, 240 requests a minute per user): `GET` returns everything, `{routines, workouts, runs, supplements, days, goals}` (routines and supplements oldest first, workouts and runs newest first, days by date; each day `{date, steps, waterMl, weightKg, taken}`, `taken` the supplements' ids); `POST /routines {id?, name, exercises: [{name, sets, reps}], notes?}` adds a routine (201), `PATCH` and `DELETE /routines/:id` change and delete one; `POST /workouts {id?, date, name, routineId?, exercises?, notes?}` adds a workout (a routine that isn't yours is left off it), `PATCH /workouts/:id {date?, name?, exercises?, notes?}` (the exercises whole: `[{id, name, sets: [{reps, weightKg, done}]}]`) and `DELETE`; `POST /runs {id?, date, distanceM, durationS, notes?}`, `PATCH` and `DELETE /runs/:id`; `POST /supplements {id?, name, dose?}` and `DELETE /supplements/:id`; `PATCH /days/:date {steps?, waterMl?, weightKg?, taken?}` changes a day of the log (`YYYY-MM-DD`, a Lisbon date; `null` clears the steps or the weight; a day with nothing logged has no row) and answers with it; `PATCH /goals {waterMl?, steps?}`. Names are 1–80 characters (a supplement's 1–60, a dose up to 40), notes up to 2,000; a routine has 1–30 exercises of 1–20 sets of 1–100 reps, a workout up to 30 exercises of up to 30 sets, each with 0–1,000 reps and 0–1,000 kg (to 0.01 kg) or none; a run 0.01–500 km in up to 99:59:59; steps up to 200,000, water up to 20,000 ml, body weight 20–400 kg (to 0.1 kg); dates are real `YYYY-MM-DD` ones. Ids are UUIDs, and clients may choose the ids of what they create; sent again with an id already yours, it answers with what is there, and one someone else has is a 409. Another user's routine, workout, run or supplement answers 404, as one that doesn't exist. `024_fitness.sql` makes `fitness_routines`, `fitness_workouts`, `fitness_runs`, `fitness_supplements`, `fitness_days` and `fitness_goals`.

## Books

`/books` keeps your private Want to Read shelf; `/books/currently-reading` and `/books/finished` open the other shelves. Search by title, author or ISBN through Open Library, or add a book manually. Catalogue results include covers and an optional page count, editable to match your edition. Open a book to change its shelf or log pages read. Reaching its total moves it to Finished; moving back to Want to Read resets progress. Remove offers Undo.

The authenticated `/api/books` API lists and adds books, `/api/books/:id` updates or deletes your own entry, and `/api/books/search?q=` searches the catalogue. Migration 025 adds `books`, with ownership, page-count constraints and a unique catalogue work per user. Books are included in Download my data and deleted with the account. Cached shelves are readable offline; changes require a connection. No catalogue API key is needed.

## Accounts, email and profile pictures

Accounts are [Better Auth](https://www.better-auth.com) ([app/auth.ts](app/auth.ts)) on the site's own tables (`016_better_auth.sql`): `users`, `accounts` (each password's bcrypt hash, [lib/password.ts](app/lib/password.ts), so passwords from before still work), `sessions` (read on every request, so logging out, a password change and deleting the account end them at once) and `verifications` (reset tokens, only their SHA-256). The forms are server actions that check their fields and rate limits and then call `auth.api`; Better Auth's same operations over HTTP are switched off (`disabledPaths`), so nothing gets around those checks. `/api/auth/*` serves the links in emails and the session. `getSession()` and `requireUser()` (in `auth.ts`) are how pages, actions and routes read the user.

Signing up sends a link to confirm the email (24 hours, [lib/auth-emails.ts](app/lib/auth-emails.ts)); until it's opened, home and `/account` say so (Send it again, sent from where it is, 3 an hour), and password resets don't go to that email. Accounts from before email confirmation count as confirmed. Changing the email in `/account` takes the current password and sends a link to the new address; the email only changes once it is opened (`Your email is changed.`), and is confirmed then, since the link proves the address (a database hook in `auth.ts`: Better Auth 1.7 would keep an account that never confirmed its first email unconfirmed), and an address another account has gets the same answer, and nothing.

`/account` has its title and the profile picture in the middle (a pencil on it says it can be changed), then a row each for Name, Username, Email (with `(not confirmed)` until it is), Theme and Password (Change, which opens Update password) with what they are now, and **Data / Privacy page** (Manage), then Log out on its own, as wide as the rows, with its icon, in the accent on its soft tint. Data / Privacy page's popup has a row each for the Privacy page, Download my data (`GET /api/account/export`, a JSON file: the account, the Shows library, friends and recommendations, the activity, and the space's members, calendar and tasks, the recipes (each with its photos' links) and shopping list, and the fitness log (routines, workouts, runs, supplements, the days logged and the goals); not the password or sessions) and Delete my account (in red; its popup, in Data / Privacy page's place, takes the password: it leaves the space, which goes with its last member, deletes the profile picture's file and the recipes' photos' files, and everything else goes with the account; then home says it's done). [/privacy](app/app/privacy/page.tsx) says what is kept, why, and who else sees it. Each row opens a popup with its form ([components/account/AccountSettings.tsx](app/components/account/AccountSettings.tsx)); Escape, a click outside or its × close it, and once saved it closes and says so under the rows. Name is one field, as sign-up has, for the name as the user wants it, `Diogo` or `Diogo Mota`: up to 50 characters, kept as typed but trimmed, with one space between words. `014_one_name.sql` made it `users.name`; accounts made before names have none until they set one, and show as their @username alone. Both apps show it with the @username, `Diogo Mota (@diogofrmota)`, or a friend's profile with the name and the @username under it ([components/common/PersonName.tsx](app/components/common/PersonName.tsx)). Theme is Light or Dark. Profile picture ([AvatarForm](app/components/account/AccountSettings.tsx)) shows the picture there is (or the username's initial) and a drop zone: a photo dragged onto it, or one chosen with a click or tap (the file picker; on a phone, the photos or the camera), opens Adjust your picture ([AvatarCrop](app/components/account/AvatarCrop.tsx)): the photo in a square with the circle that is kept marked on it, to drag (a finger, the mouse, or the arrow keys) and zoom (the slider with − and +, the mouse wheel, a pinch, or + and −). Save picture cuts that square out in the browser (a canvas, at most 1,024 px a side, WebP, or PNG where the browser can't make WebP) and sends it; it shows in the circle under a spinner until it's saved. Cancel, Escape or a click outside sends nothing. A photo the browser can't show (HEIC; TIFF outside Safari) is sent as it is, and the server decides. The tab bar's Account then has it on every page, as do Shared's members and Shows' Profile and friends. Remove picture goes back to the initial.

The server makes every picture small, though not much (a few friends use the site): [lib/avatars.ts](app/lib/avatars.ts) turns it upright as its EXIF says, cuts a square around what stands out in it (sharp's `attention` crop; a picture adjusted in the browser is already square), makes it 512 px a side and saves it as WebP at quality 82, without its metadata (such as where it was taken): 20–60 KB from a photo of several megabytes. Files up to 20 MB (`AVATAR_MAX_BYTES` in [lib/account-rules.ts](app/lib/account-rules.ts)) and 70 megapixels are taken, of any kind sharp reads (JPEG, PNG, WebP, GIF, AVIF, TIFF; not HEIC, which iPhones turn into JPEG when a photo is picked); 20 uploads per 15 minutes per user.

Each picture is a file, `AVATAR_DIR/<user id>.webp`, written beside and then renamed over the old one. `AVATAR_DIR` is `/app/data/avatars` in the image, on the `appdata` volume of [docker-compose.prod.yml](docker-compose.prod.yml), which keeps it across deploys and which [infra/backup.sh](infra/backup.sh) archives with every dump; without it (`npm run dev`) it is `app/data/avatars`, which git ignores. The database only has when it was last set, `users.avatar_updated_at` (from `012`), which is in its URL: `/api/avatars/<user id>?v=<ms>`. So a new picture is a new URL, and `GET /api/avatars/{userId}` (anyone logged in; 401 otherwise, 404 without a picture) lets browsers keep each one for a year. `POST /api/account/avatar` with a multipart form (the file as `picture`) sets yours and `DELETE` removes it; both answer `{avatarUrl}` (or an `error`) and, like the other APIs, only take changes from this site. nginx lets 21 MB through to that one path ([nginx/nginx.conf](nginx/nginx.conf)); everything else stays at 5 MB. The e2e teardown deletes the test accounts' pictures (and their recipes' photos).

## Docker image

From the repo root:

```sh
docker build --build-context migrations=db/migrations -t diogomota-com ./app
```

`db/migrations` is outside `./app`, so `--build-context` is how it gets into the image. Inside a container (Node 24), `npm run migrate` applies the migrations and `node server.js` starts the app on port 3000. What the app writes while it runs (the profile pictures and the recipes' photos) goes to `/app/data`, owned by the app's user `node`: mount a volume there to keep it. The bottom of home shows the image's version, `Version dev` unless you add `--build-arg APP_VERSION=v1.2.0` (also `dev` with `npm run dev`).

## Production

The VPS runs [docker-compose.prod.yml](docker-compose.prod.yml) (Postgres, app, Nginx, Certbot) in `/opt/diogomota`. Server setup, TLS, backups and restores are scripts in [infra/](infra/). Running it day to day (health checks, restarts, rollbacks, restoring a backup with a dry run first, the optional offsite backup, rotating secrets, certificates) is in [docs/operations.md](docs/operations.md).

### Deploys

Every push to `main` runs [.github/workflows/deploy.yml](.github/workflows/deploy.yml), one run at a time:

1. **check**: in `app/`, `npm ci`, Prettier (`format:check`), lint, typecheck, `check:migrations`, the unit tests and the build; then the Playwright tests against a Postgres service, the smoke set (`views.spec.ts` and `auth.spec.ts`). This is [.github/workflows/ci.yml](.github/workflows/ci.yml), which also runs on every pull request, there with every Playwright test; a failed run keeps its HTML report for a week.
2. **image**: builds the image, scans it with Grype (anchore/scan-action: a known critical vulnerability with a fix, in its OS packages or `node_modules`, stops the deploy, and the report is in the job's log), and pushes it to Docker Hub as `diogofrmota/diogomota-com:<tag>`, `:<version>` and `:latest`. The tag is the short commit SHA, its first 7 characters; the version (see [Versions](#versions)) is also shown on home, added to the commit as a git tag, and published as a GitHub Release listing the commits since the previous version.
3. **deploy**: over SSH as `deploy`, copies `docker-compose.prod.yml`, `nginx/`, `infra/` and `db/migrations/` to `/opt/diogomota` and runs [infra/deploy.sh](infra/deploy.sh) `<tag>` there. That pulls the image, applies pending migrations, sets `IMAGE_TAG=<tag>` in `.env`, runs `docker compose up -d app nginx`, reloads nginx and deletes old app images (it keeps the deployed one and the two newest others). The job then waits up to 60 s for https://diogomota.com/api/health to return 200; if it doesn't, the run fails and prints the app's logs.

The app container is replaced in place, so expect a few seconds of 502s. Apart from `IMAGE_TAG`, the deploy never touches `.env`, `backups/` or `logs/` on the VPS. A changed `infra/crontab` is copied but not installed: run `crontab infra/crontab` there.

The repository has one branch, `main`, and no Dependabot ([docs/decisions/0015](docs/decisions/0015-only-main.md)): updates are made by hand there, with the same checks as any change: `npm outdated` in `app/`, the GitHub Actions (pinned by commit SHA, so they never move on their own) and the Docker images, a new version only once it's a week old (fresh releases are where supply-chain attacks land), Postgres only within its major version. nginx also limits, per client address, the form submissions of the login, sign-up, reset and join pages and `/api/auth/*` (20 a minute) and the calendar subscriptions (30 a minute), which hold across deploys, unlike the app's own limits.

The workflow needs these repository secrets (Settings → Secrets and variables → Actions): `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN` (read & write), `VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY` and `VPS_KNOWN_HOSTS`. GitHub masks secret values in logs, so the Docker Hub username, the VPS address and the word `deploy` show up as `***`.

### Versions

Every deploy gets the next patch version, `vX.Y.Z`. `app/package.json` holds `X.Y.0`, and the image job sets the patch to one more than the newest `vX.Y.*` git tag (`0` if there is none yet). To move to a new minor (or major), e.g. when a new piece of work starts (see plan.md, Build log), run `npm version 1.1.0 --no-git-tag-version` in `app/` and commit: the next deploy is `v1.1.0`, then `v1.1.1`, and so on. A version other than `X.Y.0` in `package.json` fails the image job.

A failed build doesn't use up a number, because the git tag is only added once the image is on Docker Hub. Run `git fetch --tags` to get the tags locally.

### Rollback

GitHub → Actions → Deploy → Run workflow, on `main`, with `image_tag` set to the 7-character short SHA of an older commit (`git log --oneline`, the tags on Docker Hub, or `git rev-parse --short v0.6.3` for a version). This skips check and image and deploys that existing image, using the compose, nginx and infra files of the current `main`. Migrations only go forward and are never undone, so the older image has to work with the current schema.

The rollback holds until the next push to `main`, or a run with an empty `image_tag`, which deploys the newest commit again. Without GitHub, the same thing works by hand: `ssh deploy@162.19.252.190`, then `bash /opt/diogomota/infra/deploy.sh <tag>`. To see which tag is live, check the summary of the last Deploy run, or run `grep IMAGE_TAG /opt/diogomota/.env` on the VPS.

### Logs

- **Deploys**: GitHub → Actions → Deploy → the run. The summary shows the deployed tag.
- **Containers**: on the VPS, in `/opt/diogomota`: `docker compose ps` for status and health, `docker compose logs -f app` (or `nginx`, `postgres`). Docker keeps up to 3 × 10 MB of logs per container.
- **Cron jobs**: `/opt/diogomota/logs/backup.log` and `/opt/diogomota/logs/renew-cert.log`.
